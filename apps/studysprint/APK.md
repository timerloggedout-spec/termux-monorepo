# StudySprint APK surface

An Android installable carrying the StudySprint surface
(`android/`): a thin native shell (WebView) over the webApp bundle,
with the core-generated state baked in at build time. Everything
runs on-device; no network is used or requested.

**Version line: independent.** This surface versions on its own
SemVer line (owner overrule 2026-11-03), separate from the
foundation road {core v0.3.0 ⇒ v0.4.0 ⇒ v1.0.0}. Surface version =
`android/VERSION` (and the manifest `versionName`) — currently
**0.1.0** — with its own releases; the built .apk attaches to the
surface's own release.

## Build

SDK-direct, no Gradle (the fleet-apk pipeline):

```
# needs JDK 17 + Android SDK platform 34 / build-tools 34.0.0
ANDROID_SDK_ROOT=/opt/android-sdk bash android/build.sh
# -> android/studysprint.apk (signed with a generated dev key)
```

`build.sh`: regenerates the core state (`web/build_data.py` runs
the real core) → stages the webApp bundle as APK assets → aapt2
link → javac → d8 → zipalign → apksigner + verify → content smoke
(classes.dex + bundled web + state.json must be inside). In CI:
`.github/workflows/studysprint-apk.yml` builds on dispatch / on
android+web changes and uploads the `studysprint-apk` artifact.

## What's on-device

- The full webApp bundle (Today / Plan+Receipt / Reader / SR
  Review) as assets — the same screens and engines as the PWA.
- The core state (`data/state.json`) generated from the real core
  at build time — plan, trust receipt, SR cards + ts-fsrs UX
  export, reader sections.
- SR review runs on-device in the bundle's engines (FSRS via
  ts-fsrs formulas, SM-2 baseline); review state persists in the
  WebView's localStorage on the device.

Stated plainly: the Python core itself does not execute on the
phone in this version — its outputs (the state shapes every
surface consumes) are generated by the core at build time and
carried in the APK, and review scheduling runs in the bundle's
ts-fsrs/SM-2 engines. An embedded-Python build is a larger step
(BeeWare/Chaquopy class) and is not claimed here.

## Feature-parity checklist vs CLI core

| Core capability | APK | Notes |
|---|---|---|
| Study plan + trust receipt | present | baked-in core state, Plan view |
| Daily check-in | present | Today view, on-device |
| SR cards + review | present | on-device engines over the core UX export |
| Reader (RSVP) | present | bundle Reader view (beyond the filed minimum) |
| .apkg / vault export | absent | export stays CLI/TUI in this version |
| v0.4.0 core modules (§1b pipeline, courses, memory methods) | absent | parity pass pending, as on the other surfaces |

  coherence, shell wiring (asset path), build-chain completeness,
  workflow shape.
- CI build run: SDK-direct build + apksigner verify + content
  smoke, artifact uploaded (see the workflow).
- Install/run smoke on a device is the D1 seat's device-lane step
  per the issue's flow.
