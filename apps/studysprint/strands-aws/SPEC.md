# StudySprint on AWS — the Strands production span, as schemas

*Spec artifact for monorepo issue #4537 (the D1 brief is the design of
record). Machine-readable schemas live in `schemas/`; every payload
below was **derived from a golden instance** in `golden/` — captured
from live offline tool I/O, the demo run, a fresh `run_agent`
execution, and the SDK itself — and `validate_schemas.py` proves each
schema against its golden. Provider-portable by design; Bedrock-first
in the telling.*

The Strands agent already exists (`agent.py`: seven tools over a
deterministic core, an offline gate loop, and a stamped receipt for
every run). This artifact specifies the production span around it:
how it is hosted, what crosses its wires, what its receipts promise,
what it may touch, and what a judge can call. Nothing here changes
the agent; everything here makes the agent deployable without
changing its evidence discipline.

## 1 · Runtime contract — one payload, three hosts

`schemas/runtime.schema.json`. The contract is the payload; hosts
are interchangeable carriers.

- **Amazon Bedrock AgentCore Runtime (primary).** `POST
  /invocations` with an `InvocationRequest`; `GET /ping` answering
  the `PingResponse` shape (`Healthy` / `HealthyBusy` +
  `time_of_last_update`). Session affinity rides the
  `X-Amzn-Bedrock-AgentCore-Runtime-Session-Id` header.
- **Lambda (variant).** The same `InvocationRequest` arrives as the
  handler event; the same `InvocationResponse` returns. No header
  convention exists here, so the body's `session_id` field is
  authoritative — it exists in the schema for exactly this reason.
- **App Runner (variant).** Plain HTTP, same paths, same bodies;
  the header is accepted, the body field wins on conflict.

An `InvocationRequest` is a `prompt` plus, optionally, the
`run_agent` request envelope itself — so the hosted agent and the
offline gate consume *the same ask*, which is what makes the
fail-closed floor in §5 a substitution rather than a rewrite. The
response is the receipt, unenveloped: all three hosts return
byte-identical receipts for identical executions.

**Session ↔ snapshot mapping.** The runtime's session id (the
AgentCore header's value, or the body's `session_id` on the other
hosts) is used *verbatim* as the `SnapshotSessionManager`
session id (§6). The manager namespaces its writes under
`session/<session_id>/`, so a session's snapshot lands at the
storage key `session/<runtime-session-id>/snapshot.json` — one
mapping, stated once, with no translation table: a recycled
process that receives the same session id restores the same
snapshot, and a check-in written in one invocation is read back
in the next (§6).

## 2 · Tool schemas — all seven, wire and decoded

`schemas/tools.schema.json` + `schemas/payloads.schema.json`. The
SDK's `@tool` machinery (strands-agents 1.63.0) derives a toolSpec
from each wrapper's type hints and docstring. Two things follow.
First, the **wire form** is what the toolSpec says: JSON documents
travel as *strings* (`course_json`, `plan_json`, `log_json`), and
the hand-written input schemas mirror that exactly — the validator
checks property-and-required parity between the generated toolSpec
and the hand-written schema for all seven tools. Second, the
**decoded form** — what those strings parse to, and what the tool's
string return parses to — gets named schemas of its own
(`CourseDocument`, `PlanDocument`, `QuizDocument`, `TodayView`,
`CheckinLog`, `EvidenceItems`) in `payloads.schema.json`, each
`$ref`'d from the tool outputs rather than restated.

One pairing, shown in full (the other six are in
`golden/toolspecs.json` beside their `$defs` in
`tools.schema.json`):

Generated by the SDK for `make_quiz`:

```json
{"name": "make_quiz",
 "description": "Generate recall questions for one syllabus week.",
 "inputSchema": {"json": {
   "type": "object",
   "properties": {"course_json": {"type": "string",
                                  "description": "Parameter course_json"},
                  "week": {"type": "integer",
                           "description": "Parameter week"}},
   "required": ["course_json", "week"]}}}
```

Hand-written, same tool (`MakeQuizInput` / `MakeQuizOutput`): the
input adds the constraints the hints cannot carry (`week ≥ 1`), and
the output names the decoded payload —
`{"$ref": "payloads.schema.json#/$defs/QuizDocument"}`.

| tool | wire input | decoded output |
| --- | --- | --- |
| `fetch_syllabus_evidence` | `{ref}` | `EvidenceItems` |
| `make_plan` | `{course_json}` | `PlanDocument` |
| `make_quiz` | `{course_json, week}` | `QuizDocument` |
| `replan` | `{plan_json, missed_week}` | `PlanDocument` |
| `get_today_view` | `{plan_json, day_index=0}` | `TodayView` |
| `adjust_time_budget` | `{plan_json, minutes_per_day}` | `PlanDocument` |
| `checkin_session` | `{log_json, week, session_index, status}` | `CheckinLog` |

Errors share one shape (`ToolError`): the core raises ordinary
exceptions; the class name and message are the payload. There is no
invented error taxonomy for a model to misread.

## 3 · Receipt schema — the base verbatim, the live extension marked

`schemas/receipt.schema.json`. The base is the `run_agent` receipt
as it exists — keys, nullability and all (an ABSTAIN run carries
`null` plan/quiz/replan/evidence-set; the vocabularies of
`decision_*` are the golden-observed ones). Onto that base, the
live-run extension:

- `execution_class` — `offline-gate` · `live-local` ·
  `live-production`. Production receipts are *distinct* by value,
  never by implication: a receipt that decided offline says so.
- `model {provider, model_id, sdk_version}` — the model that
  actually ran, stamped per execution; provider is data, so the
  span is portable (the same agent has already run against a
  Gemini model under this discipline — monorepo issue #4534).
- `tool_trace [{tool, order, output_sha256}]` — what the model
  called, in order, with each output content-stamped.
- `fail_closed` — §5's flag.

The extension members are optional *in the schema* — the offline
goldens predate them and must keep validating — and required *by
policy* on any live receipt: a production receipt without
`execution_class` fails review, not parsing. That split is
deliberate and stated here so no reader mistakes it for laxness.

## 4 · Deployment — config, secret names, least privilege, guardrails

`schemas/deployment.schema.json` · `deployment/config.example.json`
· `deployment/iam-policy.json`.

**Config** (`DeploymentConfig`): provider, `model_id`, region, log
level, evidence root, host, and the guardrails block. The model id
is a config value, never a code constant — swapping models touches
this file alone. The Bedrock-first example names
`us.anthropic.claude-sonnet-4-5-20250929-v1:0` (the US inference
profile for `anthropic.claude-sonnet-4-5-20250929-v1:0`), **verified
against the AWS Bedrock model card at draft time**
(docs.aws.amazon.com/bedrock/latest/userguide/model-card-anthropic-claude-sonnet-4-5.html),
which lists the model in *Legacy* stage with end-of-life
2027-04-08 — inside the Nov 9–23 window it serves, and the config
being data is what makes its eventual replacement a one-line
change.

**Secrets** are referenced by Secrets Manager **name only**
(`SecretRef`: name · env var · purpose). The Bedrock route needs
none beyond the execution role; a non-Bedrock provider key, if
configured, is one named entry. No value appears in this artifact,
in git, or in a receipt — ever.

**IAM** (`deployment/iam-policy.json`), five statements, no
wildcard actions and no bare-wildcard resources (the validator
checks both):

1. `InvokeTheOneNamedModelViaItsProfile` — `bedrock:InvokeModel`
   (+ streaming) on the single named inference-profile ARN. The
   span can invoke exactly one model profile.
2. `InvokeTheProfileDestinationModels` — the same actions on the
   foundation-model ARNs in the profile's three US destination
   regions (us-east-1/us-east-2/us-west-2), enumerated rather than
   region-wildcarded: a cross-region profile resolves to those
   regions' models, and each is named.
3. `WriteTheSpanOwnLogStreams` — log-stream create/write on the
   span's own log group only. (The ARN's trailing `:*` is the
   log-stream suffix inside that one named group — streams are
   addressed no other way; it widens nothing beyond the group.)
4. `AgentStorageItemActions` — `dynamodb:PutItem` / `GetItem` /
   `DeleteItem` / `Query` on the ONE agent-storage table (§6).
   These are exactly the four operations the persistence backend
   issues at runtime (its own documentation's policy); listing is
   a partition `Query` with `begins_with`, so no `Scan` is granted
   — and no `CreateTable` / `UpdateTable`: the table is
   pre-created by the deployment (§6), and the runtime role
   cannot mint infrastructure.
5. `AgentStorageOffloadObjects` — `s3:PutObject` / `GetObject` /
   `DeleteObject` on the offload bucket's objects only (§6):
   values over the 400 KB DynamoDB item limit spill there with a
   pointer item left in the table. No bucket-level actions, no
   other bucket.

The account segment (`000000000000`) is the one deploy-time
substitution, marked here rather than disguised.

**Cost guardrails, Nov 9–23** (machine-readable in the config, not
prose): `max_tokens_per_request` 4096 · `daily_invocation_cap`
1000 · `concurrency_cap` 5 · an alarm shape (metric + thresholds +
the operator topic name). The runtime reads them and refuses past
them — refusal routes through the same fail-closed floor, never an
error page.

## 5 · Endpoint API — and the fail-closed floor

`schemas/endpoint.schema.json`.

- `POST /plan` — a syllabus in (document or resolvable reference),
  a receipt + plan out. **Always HTTP 200, always a receipt.**
- `GET /health` — liveness plus what is actually true
  (`strands_agent_available`, `deployment`, the configured model).
- `GET /receipt/{id}` — the stored receipt, byte-identical to the
  one the invocation returned. An unknown id is the endpoint's
  only 404.

**The fail-closed floor:** `POST /plan` has *no 5xx shape at all*.
On any agent or model error — throttling, a down provider, a
malformed tool call — the deterministic gate loop executes the
same request envelope and the endpoint returns its receipt with
`execution_class: "offline-gate"` and `fail_closed: true`. The
judge's request degrades to the system's most conservative honest
answer, stamped as exactly that; it never degrades to an error
page. The floor is not an error handler bolted on: it is the
offline path the system already trusts, promoted to a contract.

## 6 · Persistence — strands-dynamodb-storage, one table

The span's durable state rides **strands-dynamodb-storage**
(AWS, Apache-2.0; verified at draft time against the package's
own documentation — the AWS DynamoDB developer guide's Strands
storage page and the package README at `aws/strands-dynamodb-storage`,
commit `d858e8e1`): the SDK's unified byte `Storage` contract
(`write` / `read` / `delete` / `list`) implemented on a single
DynamoDB table. The spec's floor is strands-agents ≥ 1.48.0,
the package's stated prerequisite — the span runs 1.63.0.

**The table** (`deployment/create-table.json`, a deployable
artifact): `studysprint-agent-storage` — string partition key
`pk`, string sort key `sk`, `PAY_PER_REQUEST`. It is
**pre-created by the deployment**, never by the runtime: the
package "holds no CreateTable permission and never creates
infrastructure" (its docs), and §4's role mirrors that — the
req-1 gating is unchanged. TTL is enabled once, post-create
(`deployment/update-time-to-live.json`): the package stamps an
epoch-seconds **`expireAt`** attribute on items written with a
TTL, and reads/listings filter already-expired items before
DynamoDB physically reaps them. A constructor-bound **tenant
prefix** (`prefix="…"` — or `.namespace("…")` on the instance)
pins every operation inside one tenant's key space on the
shared table.

**What lives there.** One `DynamoDBStorage` instance, set once
on the Agent, backs every stateful subsystem, each under its
own key prefix — the wiring, verbatim from the package docs:

```python
from strands import Agent
from strands.session import SnapshotSessionManager
from strands.vended_plugins.context_offloader import ContextOffloader
from strands_dynamodb_storage import DynamoDBStorage

storage = DynamoDBStorage("studysprint-agent-storage",
                          region_name="us-east-1")
agent = Agent(
    storage=storage,
    session_manager=SnapshotSessionManager(),  # session/
    plugins=[ContextOffloader()],              # offloader/
)
```

- **Snapshots** — `SnapshotSessionManager` snapshots the
  conversation on every invocation and restores it when the
  same session returns (§1's mapping). **Check-ins survive
  runtime teardown** for the same reason: session state is in
  the table, not in the process, so a recycled Lambda or
  AgentCore environment resumes exactly where the last one
  stopped.
- **Long-term memory** — the Memory Manager speaks the same
  contract (the package ships `DynamoDBMemoryStore`); semantic
  recall via a table vector index is available but **not
  adopted here** (it would add `dynamodb:SearchVectors` and a
  Bedrock embeddings invocation to §4 — a deliberate
  non-adoption, recorded so it reads as a decision).
- **Context offload + transcripts** — oversized tool results
  under `offloader/`, transcripts under their namespace, same
  table, same four operations.
- **S3 offload shape** — values above the 400 KB DynamoDB item
  limit are offloaded to the configured bucket (constructor
  argument), with a small pointer item remaining in the table;
  §4 statement 5 scopes the role to that bucket's objects. If
  TTL is enabled on offloaded values, the bucket carries a
  matching lifecycle rule (the package docs' note).

The key mapping is the table's whole trick, and it is the
package's, not ours: a storage key's first two `/`-separated
segments become `pk`, the remainder becomes `sk` — point
operations are single-item calls, and `list` is a native
partition `Query` with `begins_with`, never a scan.

## Validation — the acceptance evidence

`python3 validate_schemas.py` (needs `jsonschema`), run at draft
time against the goldens in `golden/`:

```
PASS payload CourseDocument vs golden course
PASS payload PlanDocument vs golden plan
PASS payload QuizDocument vs golden quiz
PASS payload TodayView vs golden today view
PASS payload CheckinLog vs golden checkin log
PASS tool FetchSyllabusEvidenceInput vs wire instance
PASS tool FetchSyllabusEvidenceOutput vs decoded golden
... (all 7 tools, input + output)
PASS toolSpec parity make_quiz (generated == hand-written)
... (all 7 tools)
PASS receipt vs demo-run golden
PASS receipt vs fresh offline golden
PASS receipt live-extension instance
PASS runtime InvocationRequest vs golden ask
PASS runtime PingResponse example
PASS endpoint PlanRequest vs golden course
PASS endpoint PlanResponse vs fresh receipt
PASS endpoint HealthResponse example
PASS deployment config.example vs DeploymentConfig
PASS IAM policy: no wildcard actions, no bare-wildcard resources (5 statements)
PASS create-table artifact: pk/sk string keys, PAY_PER_REQUEST
PASS TTL artifact: expireAt enabled on the same table

ALL SCHEMA VALIDATIONS PASS
```

The validator earned its place during drafting: it caught two
hand-derivation errors against the goldens (an evidence item's
`provenance` is an object, not a string; the decision vocabulary
is `ALLOW_RECOMMENDATION`/`ESCALATE`, not an invented one). That is
the point of deriving from goldens and proving mechanically — the
schemas describe the system that exists.
