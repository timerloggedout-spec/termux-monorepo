B · Quarantine Browser Clerk C1·B

Alt names: Airlocked Web Clerk · Untrusted-Site Runner

What it is

A browser agent that does real web tasks on semi-trusted sites from a disposable Playwright profile: domain allowlists, quarantined downloads, and an action receipt for everything it does. The website is treated as hostile input — the only candidate on the slate built on that premise.

Core loop: task in → fresh disposable profile → allowlisted browsing with per-fetch logging → downloads held in quarantine → extracted data + receipt out → profile destroyed.

Signature moment: a fake re-login / verifier-download page (lookalike domain + executable) is blocked, and the task still completes in a fresh profile.

How it competes

Screen: PASS as-if-competed — C1 requirements are designed-in: Vultr VM backend, Serverless Inference for agent LLM calls, isolated sandbox, and a containment moment for the video. The brief’s own Pattern B prescribes vision-verify → human approval before final actions, and B is built around exactly that step.

Historic-pattern fit: across 11 placed projects at comparable Vultr events, proof-grounded output and enterprise workflow each appear in 10/11; formal approval gates test weak but recur as human-in-the-loop — B’s prescribed approval step matches where judging is heading.

Differentiation (Recon 🏅 depth): strongest of the C1 trio — a lookalike-domain page socially-engineering the agent itself is an unoccupied angle; market analogues (Anchor Browser, Skyvern, Browserbase) are infrastructure, not that angle. One direct in-field competitor exists (“Vex”, disposable browser sandboxes + evidence), which narrows the moat to the hostile-page/policy angle. Cleanest name on the slate.

Tiers: T1 core loop ≤ Nov 4 · T2 signature moment ≤ Nov 5 · T3 polish ≤ Nov 6 · landing Nov 7 · wall Nov 8 15:00 PT.

Main risk: browser flakiness — a flaky live demo can zero the Presentation axis on the day; the hostile fixture site must also be self-built, adding build surface. Mitigation of record: staged sites + recorded fallback (the mitigation itself reads as reliability discipline).

Kill-criterion: signature moment not demonstrable by Nov 5 EOD ⇒ descope to the T1 loop + a recorded containment artifact.

Vultr-credit fit

App VM at plans-API rates: vhp-2c-4gb-amd $0.033/h (≈$4.22/window) or 4c-8gb $0.066/h (≈$8.45/window); throwaway VM-per-task sandboxes ≈$0.01–0.05 per run, destroyed after. An agent that repairs broken code inside disposable sandboxes while planted adversarial probes attack every patch — edge cases, regressions, hostile inputs. A fix counts only when it survives the full test barrage; the surviving test log, not the agent’s claim, is the proof, issued as a pass/fail evidence receipt.

Core loop: broken code in → agent patches in-sandbox → test suite + attack probes run → surviving fix ships with a signed receipt → sandbox destroyed.

Signature moment: a probe tries to exfiltrate a canary secret → egress denied, process killed, sandbox destroyed, and a clean rerun completes with a signed receipt.

How it competes

Screen: PASS as-if-competed — C1 requirements designed-in (VM backend, Serverless Inference, isolated sandbox, containment moment in video). Containment is the product itself, and the receipt pattern is fleet-native (evidence envelopes, repo-owned receipt ledgers), so the proof layer is inherited pre-built rather than invented in-window.

Historic-pattern fit: strongest on the slate alongside E — adversarial proof artifacts map directly onto the proof-grounded leg (10/11 placed projects at comparable events).

The execution/proof-depth case is unchanged; the originality case is weakened. Field evidence agrees: the first 3 event submissions were all generic C1 runtimes, and prove-it/witness-style entries are already in the field — A’s separation is adversarial survival, not claim-proof.

C · Dependency Detox Chamber C1·A

Alt names: Clean-Room Upgrade Bay · Supply-Chain Airlock

What it is

Dependency upgrades processed inside an isolated chamber: every new package version is resolved, installed, and scanned in-chamber first, because install scripts are untrusted code. Flagged packages stop at the door with a scan report attached; only verified-clean upgrades reach the codebase — as a proven migration patch, not a bare version bump — with a toxic-version ledger kept of everything blocked.

Core loop: upgrade proposed → install in isolation under registry-only egress → scan + behavior check → clean version exits as a migration patch; toxic version is killed and ledgered.

Signature moment: a postinstall script writes outside the workspace and calls a non-registry host → killed, the version is marked toxic in the ledger, and the upgrade completes safely on a clean version.

How it competes

Screen: PASS as-if-competed — C1 requirements designed-in (VM backend, Serverless Inference, isolated sandbox, containment moment in video). Its containment is an egress allowlist: enforceable and binary-provable, not theatre.

Historic-pattern fit: proof-grounded leg strong (scan reports + toxic ledger are verifiable artifacts, and the receipt-ledger pattern is fleet-native); enterprise-workflow leg moderate (a utility, not a multi-party workflow).

Differentiation (Recon 🏅 depth): PARTIAL — SafeDep (pre-install sandboxing of install scripts) and Socket (install-script exfil flags) are adjacent, so the delta narrows to two things: registry-only egress as demonstrated containment, and output = a proven migration patch rather than a bump PR or a block verdict. Field OSINT found no supply-chain signal in the sampled field, so in-event room is real (“Detox” itself is a generic phrase and an existing JS testing framework’s name — noted, not blocking).

Build effort / risk

Main risk: ecosystem edge cases — pin npm XOR pip; the “utility” read also makes the Presentation axis weaker than A’s arena (counter: the toxic-version ledger is a screenshot-able artifact judges grasp in seconds).

Kill-criterion: signature moment not demonstrable by Nov 5 EOD ⇒ descope to the T1 loop + a recorded containment artifact.

Vultr-credit fit

E · Three-Way Match Room C2

Alt name: Match Exception Desk · Field flag: ledgerpilot works adjacent AP territory — “ledger” stays out of this candidate’s naming

What it is

An accounts-payable agent that matches every purchase order against its invoice and goods receipt, line by line. Exact three-way matches pass untouched; only exceptions route to a human, each flagged with the exact conflicting fields, and the close produces an audit-ready packet. Staff work discrepancies instead of re-checking the clean majority.

Core loop: PO + invoice + receipt in → deterministic line-by-line match → clean matches pass → exceptions routed with agent-proposed resolution → controller approval → audit-ready close packet.

Signature moment: a duplicate, price-variance invoice is traced to an amended PO → credit-memo task + approval packet produced in one pass.

How it competes

Screen: PASS as-if-competed — C2 requirements met (Vultr VM backend + web app; inference optional, used for extraction). Deterministic matching core gives it the highest demo reliability on the slate: rules, not model luck.

Historic-pattern fit: strongest on the slate alongside A — the audit pack plus controller approval is the slate’s most explicit gate, mapping onto both the proof-grounded leg and the enterprise-workflow leg (each 10/11 at comparable events).

Differentiation (Recon 🏅 depth): WEAK, stated honestly — the feature set is the category definition: Coupa, Medius, Tipalti, Stampli, Basware, SAP Concur, and Vic.ai all ship three-way match + exceptions + approval + audit. Differentiation must ride audit-pack quality and the agent-proposed resolution, never the match itself. In-event room is nonetheless real: the field skews C1, and exactly one adjacent C2 signal (ledgerpilot, procurement reconciliation) was found.

Build effort / risk

No outreach sends itself.

Core loop: stall detection → account brief → rescue draft → human approval → CRM update + follow-up → audit timeline.

Signature moment: a stalled deal is diagnosed from its activity evidence and a rescue draft is approved and written back to the CRM in one closed loop.
