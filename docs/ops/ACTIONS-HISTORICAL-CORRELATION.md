# Actions ↔ Historical Evaluation Correlation Matrix

## Purpose

`#390` is a churn case study, not the boundary of evaluation. The authoritative evaluation population is the repository's **entire observable history**: issues, issue comments, pull requests, commits, reviews, review comments, workflow runs, jobs, steps, artifacts, branches, and benchmark/fork lineage.

## Correlation matrix

| Event / object | Stable join key | Correlate with | Evaluation dimensions | Evidence output |
|---|---|---|---|---|
| Issue | issue number + node ID | commits, PRs, comments, runs | intent, scope, churn, outcome | event ledger |
| Issue comment | comment ID + issue number | author, issue, subsequent commits/runs | decision/change lead-lag | event ledger |
| PR | PR number + head/base SHA | commits, reviews, comments, runs, artifacts | change effectiveness, review signal, churn | PR ledger |
| Commit | SHA | PRs, runs, files, parent lineage | change, regression, survival | SHA evidence envelope |
| Review | review ID + PR | commit/SHA, reviewer/agent | critique signal, acceptance, regression | review ledger |
| Review comment | comment ID + PR/SHA/path | review, commit, subsequent fixes | defect detection and resolution | comment ledger |
| Workflow run | run ID + head SHA | workflow/job/step/artifact + PR/commit | execution, failure, latency, replication | run ledger |
| Job / step | job ID / step name | run ID + SHA | boundary failure, retries, resource behavior | run telemetry |
| Artifact | artifact ID + run ID | SHA/run/experiment | reproducibility, model/provider output | immutable artifact |
| Branch | ref + tip SHA | PRs, commits, runs | alternate attempts / lineage | provenance graph |
| Benchmark case | benchmark/task ID | treatment + repo SHA | correctness, trajectory, environment | AEF result |
| Fork | repository + source lineage | benchmark/task/treatment | agent implementation lineage | cohort registry |

## Required dimensions

Every evaluable event may contribute to the multidimensional matrix:

`provider × model × agent × prompt × manager × cohort × sequencing × task × evaluator × blindness × repository_ref × workflow × tool/API boundary`

These are **factors**, not assumptions about quality. Outcomes remain separate from route execution, latency, cost, quota, or availability.

## BIUDL cycle

1. **Broad** — discover all new/changed GitHub objects and candidate forks/benchmarks.
2. **Integrate** — join them through SHA, IDs, refs, timestamps, workflow/run IDs, and relationship-graph edges.
3. **Validate** — evaluate historical and current evidence; replay deterministic/custom-environment cases where possible.
4. **Develop** — make the smallest evidence-backed change.
5. **Learn** — append receipts, update SSOT/skills, score contribution/effectiveness, and identify new experiments.
6. **Loop** — automatically repeat; do not reset the historical baseline.

## Actions integration

`.github/workflows/historical-evaluation-correlation.yml` periodically snapshots the repository's GitHub history and publishes an immutable correlation artifact. It also checks that workflow filenames referenced by `docs/**/*.md` still resolve.

`.github/workflows/continuous-evaluation.yml` remains the live provider/model experiment loop; its dynamic matrix is a treatment population, not the historical ledger.

The historical ledger therefore answers **what happened**, while AEF/MVT/DOE answers **what happened under which treatment and with what outcome**.

## Staleness policy

Documentation that names a workflow is treated as a dependency. Missing workflow references are surfaced automatically. Generated/index documents should be regenerated by their owning workflow rather than manually treated as authoritative.

No manual audit gate is required: audit is an automated evidence-producing process. A finding may still produce an audit PR/branch so the correction has normal Git provenance.
