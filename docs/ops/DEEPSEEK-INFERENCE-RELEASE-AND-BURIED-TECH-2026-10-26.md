# DeepSeek's inference release cluster — lessons, plus a buried-tech sweep

[MUSEai]@{role:{deepseek-watch}} — landed under the main lane's assignment 2026-10-26. Companion entries in `config/agent_stack_integrations.json`: `deepseek-deepinfer`, `deepseek-deepspec-dspark`, `mooncake-kvcache`, `lmcache-cacheblend`, `trailofbits-buttercup`, `skypilot-compute-broker`, `ttt-e2e` (all WATCH except Buttercup, INVESTIGATE). All facts below are from primary sources (DeepSeek's own repos, the DSpark paper, the Hugging Face model card, project READMEs, arXiv abstracts) unless explicitly marked vendor-reported or secondary.

## 1. What DeepSeek actually shipped — the phrase "inference training" maps to two things

There is no product named "inference training." The owner's phrase resolves to a release cluster, verified from the `deepseek-ai` GitHub org and Hugging Face:

- **DeepSeek-V4.1-Flash-1017** (checkpoint, 2026-10-17). A "minor update" per its own model card, served under the unchanged `deepseek-flash` API model string (per DeepSeek's docs, as reported by secondary coverage of the release notes). Card-reported gains concentrate in agentic/coding benchmarks (Terminal-Bench 4.0: 31.2 → 42.3; ProgramBench: 20.3 → 29.1; DeepSWE v1.1: 74.2 → 77.0), with reduced task time and output length. The card ships **no Jinja chat template** — a Python reference encoder (`encoding.py`) instead. Weights MIT, 1M context. Secondary coverage attributes the gains to reinforcement-learning post-training with self-feedback, tuned for agent harnesses (DeepSeek Harness, Tencent CodeBuddy/WorkBuddy); the card itself does not state the training recipe, so that attribution stays secondary-grade.
- **DeepInfer** (repo created 2026-10-16, announced 2026-10-20; Apache-2.0). DeepSeek's production inference framework, open-sourced. Built primarily on vLLM, with SGLang/TensorRT-LLM inspiration. This release is **offline inference only, one model (V4.1-Flash), two datacenter hardware families** (NVIDIA SM100 / CUDA 13; Huawei Ascend 950 / CANN 9.2). Features: FlashMLA / DeepGEMM / DeepEP / TileKernels / DeepSelect kernels, attention-DP + balanced context parallelism, MoE expert parallelism with EPLB, DSpark with confidence-scheduled verification, SWA bounded replay, zero-overhead async scheduling, **batch-invariant inference**, **deterministic sampling**, structured outputs (regex / JSON schema / EBNF).
- **deepseek-recipe** (released alongside). Rust libraries with Python bindings that convert Messages / Chat Completions / Responses API requests into DeepSeek's native conversation format and back — i.e., a maintained parity layer so third-party stacks encode prompts exactly as the official API does.
- **DeepSpec + DSpark** (repo 2026-06-26; paper arXiv:2607.05147, submitted 2026-07-06) — the literal "training for inference" artifact, now load-bearing inside DeepInfer. DeepSpec is a full-stack codebase for **training and evaluating speculative-decoding draft models** (DSpark, DFlash, Eagle3), with released draft checkpoints for Qwen3-4B/8B/14B and Gemma-4-12B targets. DSpark's two moves, from the paper abstract: a **semi-autoregressive drafter** (parallel backbone + lightweight sequential module) that fixes parallel-draft suffix decay, and **confidence-scheduled verification** — verification length per request is tailored from estimated prefix-survival probabilities and engine throughput profiles, instead of verifying every drafted block indiscriminately. Production claim (paper, DeepSeek-reported): deployed in the DeepSeek-V4 serving system under live traffic, DSpark accelerated per-user generation **60–85% over the MTP-1 baseline at matched throughput**.

Also explicitly on the record, from DeepInfer's README — **what the open release does not include**: a KV cache system, prefill/decode disaggregation, and load balancing across replicas. The engine is the compute core, not the serving system. Press coverage of DeepSeek's production figures (≈155T tokens/day per cluster, 96% input cache-hit rate, ~400 ms TTFT, 230 tok/s per user) describes the unreleased surround, is vendor-reported, and is not independently verified.

## 2. Lessons for this fleet (concrete, in force order)

**L1 — A provider model string is a moving checkpoint; weight accordingly.** V4.1-Flash-1017 replaced the model behind `deepseek-flash` with no API change. Any MVT/DoE weighting keyed on (provider, model string) alone will silently mix two checkpoints' delivery data. Rule: weighting and delivery metrics key on (provider, model string, observation window), announced checkpoint dates are re-baselining events, and a sudden delivery/performance shift is investigated as a possible checkpoint swap before it is read as drift. This is the provider-side twin of this repo's own phantom-snapshot lesson.

**L2 — Schedule verification by confidence; don't verify everything uniformly.** DSpark's transferable move is not the drafter, it's the scheduler: verification budget follows estimated survival probability. The same shape already exists in this fleet three times — reviewer JIT (verification effort follows context), quota-aware bot cadence (dispatch follows reconciled quota), the Delphi gate — but none of them yet allocates by a measured acceptance signal. Where a lane both drafts and verifies (peer review, tribute S1 ladder, RFP panels), record acceptance rate per drafter and let it set verification depth. Acceptance rate is the DoE-measurable quantity; DeepSpec's eval suite (gsm8k, math500, aime25, humaneval, mbpp, livecodebench, mt-bench, alpaca, arena-hard-v2) is a worked example of pinning it to a fixed benchmark set.

**L3 — Draft/accelerator training is a pipeline, and the bill is data, not training.** DeepSpec's workflow is: regenerate target answers → build a target cache → train the draft against the cache → evaluate acceptance. Its README's own warning: the target cache for the default Qwen3-4B setting runs to roughly **38 TB**. Any future fleet self-host experiment (e.g., a draft model for a local llama.cpp lane) budgets storage and regeneration compute first; the training step is the cheap part.

**L4 — Determinism is a shipped feature, not an accident; eval lanes must pin it.** DeepInfer ships batch-invariant inference and deterministic sampling (batch-invariance + fixed `seq_seed`) as explicit toggles, because results otherwise vary with batch composition. Fleet rule for any self-hosted eval or DoE run: pin batch invariance / seed, or record batch composition as an evidence field — an unpinned comparison is confounded before it starts. (Consistent with this catalog's standing rule that simulation, live, review, and provenance evidence stay separate.)

**L5 — Prompt-format parity is a controlled variable.** DeepSeek ships a reference encoder plus a maintained Rust parity toolkit because token-level encoding differences silently change model behavior. In cross-provider DoE, encoding/parity drift is a confound of the same class as L1's checkpoint swap: when a comparison moves, check the encoder before crediting the model.

**L6 — The production lesson is cache economics, and it has an API-side analogue.** The most decision-relevant vendor-reported number in the cluster is the 96% input cache-hit rate: at scale, serving cost is dominated by how much prefill you *don't* recompute. The fleet buys API inference, not GPUs, so the analogue is prompt construction: prefix-stable prompts (stable system/context blocks first, variable content last) maximize provider-side prefix-cache hits across the callable-inference lanes, and per-provider cache-hit / cached-token telemetry belongs in the weighting inputs next to price and delivery. (See §3 items 1–2 for the research line that generalizes this beyond prefixes.)

**Posture.** DeepInfer itself is **not fleet-runnable** — SM100/Ascend-950 datacenter hardware, offline mode, single model; the fleet has no GPU estate and the B160V law forbids pretending otherwise. Status WATCH, patterns-to-mirror (L2, L4, L6). DeepSpec likewise WATCH: no fleet draft-training today, but its metrics discipline (L2, L3) applies now. Neither enters routing.

## 3. Buried-tech sweep — surfaced in academic venues, competitions, and community repos; absent from mainstream coverage and, until now, from this fleet's map

Ranked by fleet fit. "Buried" is graded honestly per item: several are well-known *inside* the serving community while invisible outside it; the genuinely low-visibility items are marked.

1. **Mooncake** (kvcache-ai/Mooncake; **Best Paper, USENIX FAST 2025**; the serving platform behind Moonshot's Kimi). A KVCache-centric disaggregated architecture: prefill/decode pools plus a distributed KV cache (Mooncake Store) treated as the system's center of gravity, with published anonymized production traces for reproducible workload research. Surfaced via a systems conference and the LMSYS/SGLang ecosystem (it is now SGLang's KV backend), not via product press. Fleet fit: the reference design behind L6 — and its open traces are ready-made DoE workload evidence if the fleet ever evaluates self-host serving. **WATCH.** (6.9k stars, actively pushed.)
2. **LMCache + CacheBlend** (LMCache/LMCache; CacheBlend: Yao et al., UChicago, **EuroSys 2025**, arXiv:2405.16444). LMCache is a KV-cache layer across engines and instances; CacheBlend is its research core — reuse of precomputed KV for chunks at **any** position (not just prefixes), selectively recomputing a small subset of tokens to restore cross-attention quality: TTFT down 2.2–3.3×, throughput up 2.8–5× vs full recompute in the paper. Buried in a EuroSys proceedings paper while the industry marketed plain prefix caching. Fleet fit: defines the real frontier of context reuse for retrieval-heavy agent flows; sets correct expectations for what provider "prompt caching" can and cannot do. **WATCH.** (12.2k stars — known in the serving community, invisible outside it.)
3. **Buttercup** (trailofbits/buttercup) — *genuinely buried relative to capability.* Trail of Bits' Cyber Reasoning System from the **DARPA AIxCC** competition: an autonomous pipeline that finds *and patches* software vulnerabilities, open-sourced after the competition with a fraction of the attention the competition's winners received in security press. Fleet fit: direct candidate for the security-evidence side of this repo's review system — the ECC findings queue disposition work is today a manual, findings-only process; a find-and-patch CRS is the adjacent capability, from a primary-source-grade vendor. **INVESTIGATE** (scoped evaluation against the ECC/security-evidence workflow; no adoption implied). (1.7k stars.)
4. **SkyPilot** (skypilot-org/skypilot; Berkeley Sky Computing lineage). One interface over every cloud's GPU/CPU capacity — including spot and free-ish tiers — with cost as a first-class placement objective. It lives in academic/systems circles and word-of-mouth, not in the agent-builder mainstream. Fleet fit: the natural broker if any lane ever needs burst or self-host overflow compute, and its cost-weighted placement model is MVT-shaped. Blocked today by the same fact as ACE: no fleet cloud accounts (card rule). **WATCH.** (10.8k stars.)
5. **TTT-E2E — End-to-End Test-Time Training for Long Context** (arXiv:2512.23675, Dec 2025; Astera Institute, NVIDIA, Stanford, UC Berkeley, UC San Diego) — *buried under the generic "test-time compute" flood.* Reframes long context as continual learning: a plain sliding-window Transformer keeps training on the context at test time, compressing it into weights, with the initialization meta-learned for exactly that. Reported: scaling behavior matching full attention with constant per-token latency, 2.7× faster than full attention at 128K context (3B model, 164B training tokens); code public. Fleet fit: research watch for DeepAgent/deepcli context strategy — the context-into-weights pole of the design space, against today's retrieval pole. No near-term application; the fleet runs no trainable local model at this scale. **WATCH, research-only.**
6. **SpecForge** (sgl-project/SpecForge) — noted, no separate catalog entry. The SGLang community's draft-model training framework (1.2k stars) is what DeepSpec itself builds on (DeepSpec's NOTICE/README credit it for the framework and Eagle3 implementation). Its significance is directional: draft-model training has already commoditized into community tooling, which is evidence for L3's framing — the scarce asset is target-generated data and acceptance telemetry, not training code.
