# Device Pull-Queue — Runbook (P1, Phase 1)

The rendezvous that replaces push-based device tasking (SSH manifest + tunnel
+ opaque on-device scheduler) with a pull model: producers enqueue tasks to a
small Cloudflare Worker backed by D1; devices poll outbound HTTPS, claim one
task atomically, run it locally, and post a receipt.

**Design of record:** `docs/ops/P1-PULL-QUEUE-SPEC.md`.
**Phase 1 (this document's code):** Worker + D1 schema + `queuectl` CLI +
account-free tests. **Phase 2** (device poller, Termux job 43112) and
**Phase 3** (Actions producer workflow) are separate follow-ups — nothing in
Phase 1 touches a device or a workflow.

## Architecture

```
 producers                          rendezvous (Cloudflare Free)        devices
 ─────────                          ────────────────────────────          ───────
 Actions (Phase 3) ─POST /tasks──▶  Worker  ops/device-queue/worker/     Termux poller
 queuectl (owner)  ──POST /tasks──▶    │  D1: tasks + events ledger       (Phase 2)
 chats             ──POST /tasks──▶    │  binding: DB                       │
                                       └──── GET /tasks/next (claim) ──────┘
                                             POST /tasks/:id/receipt
                                             POST /tasks/:id/release
 fallback: device-queue git branch, same task/receipt JSON shapes (spec §10)
```

Key invariants:

- Payloads are references, not blobs (≤ 4096 bytes, JSON). Larger artifacts
  live in the repo or R2 and are referenced by path/URL.
- Task kinds are an allowlist: `deepagent-run`, `git-commit-push`, `git-sync`,
  `shell-allowlisted`, `heartbeat-only`. No free-form remote shell in v1.
- Claims carry a 45-minute lease. A reaper inside every claim request returns
  expired leases to `queued` (or `dead` at `max_attempts`) and marks
  TTL-expired queued tasks `expired`. No cron is required.
- Every receipt carries `storage_free_mb`, so each completed task doubles as
  a device-storage telemetry point.
- Write budget: one task lifecycle ≈ 6–10 D1 row-writes against the 100k/day
  free cap. At 80,000 event rows/day the Worker refuses new enqueues with
  `503 { "error": "write_budget" }` rather than dying mid-claim.

## API summary

All routes require `Authorization: Bearer <token>` except `GET /health`.

| Route | Actor | Notes |
|---|---|---|
| `POST /tasks` | producer | `201 {id, state:"queued"}`; duplicate `dedupe_key` → `409` with the existing id; bad kind or payload > 4096 bytes → `400`; write budget → `503` |
| `GET /tasks/next?role=<role>` | device | Reaps, then atomically claims the oldest claimable task: `200 {task}` or `204` |
| `POST /tasks/:id/receipt` | device (claimant only) | Sets `done` when `receipt.completion_status == "completed"`, else `failed`; non-claimant → `403` |
| `POST /tasks/:id/release` | device (claimant only) | Returns the claim to `queued` without consuming an attempt |
| `GET /tasks/:id` | producer, or the claiming device | Full row including receipt |
| `GET /health` | public | Counts only: `{ok, queued, claimed, dead, oldest_queued_age_s, at}` |

Auth errors: missing/unknown token → `401`; valid token, wrong role → `403`.
Tokens are compared in constant time and are stamped on rows as labels
(`producer:*` / `device:*`), never stored as values.

## Deploy (owner step)

Deploy is an **owner step**: it needs the fleet Cloudflare account and the
token values, which never enter the repo, chat, or CI. From a workstation
with wrangler authenticated to the fleet account:

```bash
cd ops/device-queue/worker

# 1. Create the database; copy the printed database_id into wrangler.toml,
#    replacing REPLACE_AT_DEPLOY (commit that one-line change).
npx wrangler d1 create tmx-device-queue

# 2. Apply the schema.
npx wrangler d1 execute tmx-device-queue --remote --file=schema.sql

# 3. Set the four token secrets (values generated by the owner; names only
#    ever appear in the repo).
npx wrangler secret put DEVICE_QUEUE_PRODUCER_TOKEN_ACTIONS
npx wrangler secret put DEVICE_QUEUE_PRODUCER_TOKEN_CLI
npx wrangler secret put DEVICE_QUEUE_DEVICE_TOKEN_PRIMARY
npx wrangler secret put DEVICE_QUEUE_DEVICE_TOKEN_SECONDARY

# 4. Deploy.
npx wrangler deploy

# 5. Smoke: health is public; enqueue + show need a producer token.
curl https://tmx-device-queue.<account>.workers.dev/health
DEVICE_QUEUE_URL=https://tmx-device-queue.<account>.workers.dev \
DEVICE_QUEUE_TOKEN=<producer value> \
  python3 ../queuectl.py enqueue --kind heartbeat-only --dedupe smoke-1
```

Distribute token values to their holders through the vault route only
(Actions secret for the Phase 3 producer; each device's
`~/.config/tmx-device/queue.env`, mode 600).

## Token rotation

1. Generate the replacement value.
2. Update the holder first where possible (device `queue.env` / Actions
   secret), then `wrangler secret put <NAME>` with the new value and
   redeploy — or, to avoid any gap, temporarily accept both by rotating the
   *label pair*: put the new value under the other producer secret name
   (the two producer labels are interchangeable for enqueue/show), switch
   holders, then retire the old name's value by replacing it with a fresh
   unused value.
3. Verify with `queuectl.py health` + one `show` per rotated holder.
4. Record the rotation (date + secret name only) in the lane log. A leaked
   device token can only claim/receipt allowlisted kinds for its own device
   label; a leaked producer token can only enqueue allowlisted kinds — the
   on-device allowlist remains the real boundary (spec §7).

## Failure table

| Failure | Behavior |
|---|---|
| Worker/D1 down or account lost | Poller exits 0, logs, retries next cycle; producers fall back per spec §10; `/health` absence is itself the down-new signal for the census poll |
| Device offline > lease | Claims reap automatically (§6 of the spec); nightly tasks expire rather than pile up |
| Duplicate enqueue | `dedupe_key` unique → 409 with existing id; nightly producers use `dq-<yyyymmdd>-<kind>` keys |
| Payload > 4 KB / bad kind | 400 at enqueue; on-device revalidation is the second gate |
| D1 write budget pressure | Lifecycle ≈ 10 writes/task; at the safety-0.8 line (80k/day) the Worker refuses new enqueues with `503 { error: "write_budget" }` rather than dying mid-claim |
| Token leak | Rotation above (§7 of the spec); blast radius bounded by allowlists on both sides |

## Day-to-day operation

```bash
export DEVICE_QUEUE_URL=https://tmx-device-queue.<account>.workers.dev
export DEVICE_QUEUE_TOKEN=<producer value>

python3 ops/device-queue/queuectl.py health
python3 ops/device-queue/queuectl.py enqueue --kind git-sync --dedupe nightly-20261022-sync
python3 ops/device-queue/queuectl.py show dq-20261022-abc123
```

A `dead` count above zero in `/health` means tasks exhausted their attempts —
inspect them with `show`, fix the cause, and re-enqueue under a new
`dedupe_key` (dead rows are terminal by design; they are the audit trail,
not a retry queue).
