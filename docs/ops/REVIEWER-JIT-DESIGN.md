# Reviewer JIT — context-adapted reviewer settings, mapped with performance metrics

**Directive (owner, 2026-10-23):** "CodeRabbitAI && others settings .yaml
required to be JIT adapted to each context & mapped with performance
metrics." Static one-size reviewer settings are superseded by per-context
adaptation whose every rule is measured. This document is the design of
record; adaptations are appended to the log in §9 as they land.

## 1. Recon summary (2026-10-23, live reads)

- Exactly **one vendor settings file** exists in the repo:
  `.coderabbit.yaml` (was 612 B, fully static — none of CodeRabbit's
  context axes in use). Qodo / Devin / Copilot / Aikido / Sentry have **no
  config files**; they exist only as entries in the orchestrator's
  provider maps.
- The **peer-review orchestrator** (`.github/workflows/peer-review-orchestrator.yml`)
  is the real control plane: provider registry in code, trigger commands
  for coderabbit/qodo/devin, SHA-bound state comments as the audit trail,
  and a repo-variable policy layer that was **entirely unset** (every
  policy ran on in-code defaults).
- The Gemini lane is already JIT-shaped (model-router action chooses
  provider+model per role from a live catalog; the second pass is gated
  on verified peer state). CellCog has one variable knob
  (`CELLCOG_CHAT_TIER`). ECC Tools is comment-only by vendor design; its
  repo-side levers are cadence knobs in `agent-ecc-tools-ops.yml`, and
  its `.claude/ecc-tools.json` profile is app-generated (read-only
  evidence, not a lever).
- **Metrics substrate:** the orchestrator's state comments carry
  provider × PR × SHA × cycle with timestamps, states, evidence URLs and
  cooldowns. Nothing aggregated them; no reviewer-provider weighting
  existed (Moneyball/DoE covers PRs and quotas, not reviewers).

## 2. Architecture — three adaptation layers

| Layer | Cadence | What adapts | Where |
|---|---|---|---|
| Orchestrator collect step | per PR, per cycle | effective required provider set; context recorded per cycle | `peer-review-orchestrator.yml` |
| Repo variables | instant, no commit | baseline policy (required set, enforcement, allowed actions, executor/publisher logins, CellCog tier) | Actions variables (§6) |
| Vendor settings file | commit cadence | CodeRabbit's own context axes: `path_filters`, `path_instructions` | `.coderabbit.yaml` |

The **metrics map** (§5) feeds layers 1 and 3: it is regenerated by
`scripts/reviewer_metrics/collect.py` (workflow
`reviewer-metrics-collect.yml`, weekly + dispatch) and proposed as a
refresh PR — never committed by the collector directly. The orchestrator
reads the map from the default branch at cycle time and **fails open**:
a missing, unparsable, or >14-day-old map disables metrics-driven rules
for that cycle; structural rules still apply.

## 3. Context schema (recorded in every state comment)

The collect step derives and publishes:

- `context_author` / `context_author_class` — PR author login; `bot` when
  the author type is Bot or the login ends in `[bot]`, else `user`.
- `context_primary_class` / `context_classes` — change classification of
  the PR's files (counts per class), per the shared rules in §4.
- `context_size` — `files=…, additions=…, deletions=…` from the PR object.
- `context_labels` — sorted PR labels.
- `metrics_map` — `generated_at` of the metrics map consumed this cycle,
  or `unavailable`.

The context key used by the metrics map and the policy rules is
`<author_class>/<primary_class>` (e.g. `bot/mixed`, `user/workflows`).

**Contract safety:** the new fields are appended *after* the existing
field block. `gemini-after-peers.yml` locates the state comment by the
v2 marker + `cycle_id:`/`head_sha:` and first-match-parses `state:` /
`ready:` — appended fields cannot shadow them (verified against its
source before landing).

## 4. Change-class rules (SSOT — two implementations, parity-tested)

Implemented identically in `classifyFilePath` (orchestrator JS) and
`classify_file` (`scripts/reviewer_metrics/collect.py`); a 31-path
parity test passes. First match wins:

1. `generated` — under `docs/ops/generated/` or any `/generated/` segment
2. `workflows` — under `.github/workflows/`
3. `docs` — under `docs/`, or basename ends `.md` / `.rst`
4. `tests` — under `tests/`, any `/tests/` segment, basename starts
   `test_`, ends `_test.py`, `.test.js`, `.spec.js`
5. `config` — extension `toml` / `yaml` / `yml`
6. `code` — extension `py js ts tsx jsx go rs sh bash c h cpp java rb`
7. `data` — extension `json jsonl csv`
8. `other` — everything else

**Primary class** = the sole class, or the class holding a *strict
majority* of the PR's files; otherwise `mixed`. No files → `unknown`.

## 5. Metrics map — schema `reviewer-metrics/v1`

`docs/ops/generated/reviewer-metrics.json`, produced by
`scripts/reviewer_metrics/collect.py` (stdlib only). Per provider:
totals + `by_context` buckets keyed by the §3 context key; the raw
per-cycle records are included for drill-down. Metric definitions:

- **cycles / required_cycles** — state-comment cycles where the provider
  appears / is in the cycle's effective `required_providers`.
- **delivered** — per the orchestrator's own delivery definition: a
  review or review comment from the provider's bot login bound to the
  cycle's head SHA at/after `cycle_started_at`, or the state line
  `provider_completed`. (The state line alone undercounts — it is a
  snapshot that only advances when a later event re-triggers collect.
  Check-run evidence, the orchestrator's third channel, is not
  reconstructed by the collector in v1.)
- **delivery_rate** = delivered / required_cycles.
- **median_latency_sec** — median of (first delivery evidence −
  cycle_started_at) over delivered cycles.
- **cooldown_cycles** — cycles whose final provider state was
  `provider_cooldown`.
- **verdicts / review_comments / issue_comments** — PR-level data,
  counted **once per PR** (they are carried on every cycle record of
  that PR; summing per cycle double-counts).
- **by_author_class** (round 2) — the same bucket fields rolled up per
  author class (`bot` / `user`) across all contexts. Per-context keys
  fragment author-class-wide failure modes; the rollup sees them whole.
- **ECC findings** (round 2) — ECC is comment-only, so delivery rate is
  the wrong axis for it. The collector parses its pr-audit comments
  (marker `ecc-tools:pr-audit:<gate>:<sha>`, verdict line carrying a
  check-vocabulary conclusion) and reports `providers.ecc.findings`:
  audit volume, `action_required` findings split by PR state (open =
  undispositioned; closed = dispositioned or moot — PR state is the
  proxy), findings bound to the PR's current head, and a per-gate
  breakdown.
- All figures are derived from live API responses at collection time.
  Nothing is copied forward from earlier snapshots.

## 7. Policy rules v1 (orchestrator collect step)

1. **Bot-author rule (structural).** CodeRabbit does not review
   bot-authored PRs without an assigned review seat; the owner declined
   the seat (2026-10-23). For bot-authored PRs, `coderabbit` is dropped
   from the effective required set; state line
   `not_required_bot_authored_pr`. (Landed first as PR #1628.)
2. **Zero-delivery rule (metrics).** If the fresh metrics map shows a
   required provider with **zero deliveries over ≥10 required cycles in
   this cycle's exact context key**, it is exempted for the cycle; state
   line `not_required_zero_delivery_in_context` with the map timestamp
   and cycle count in the note. This is the general form of rule 1: it
   fires only on total non-delivery in context, never on low-but-nonzero
   delivery.
2b. **Author-class rollup evaluation (round 2).** When the per-context
   bucket does not qualify, the rule also evaluates the provider's
   `by_author_class` rollup for the cycle's author class under the same
   threshold (≥10 required, 0 delivered), and exempts with a rollup note.
   Motivated by the widened map: bot contexts held 10 required cycles
   across 6 keys with zero deliveries — total non-delivery no single
   context key could see.
4. **Cooldown-aware triggering (round 2).** When a provider's cooldown
   notice states a retry duration, collect computes the window end
   (notice time + duration), records it in the state comment
   (`cooldown_until=`) and in the `provider_cooldowns` output. The
   OPERATOR request step defers a provider's trigger request while its
   recorded window is still in the future — requests inside a known-dead
   window are deferred, not spent. Unknown windows change nothing.
5. The OPERATOR request step consumes the effective set, so exempted
   providers are not trigger-requested either.

**Refuted during design (kept for the record):** a docs-only exemption
for CodeRabbit was drafted a priori — and dropped before landing,
because the first metrics map showed `user/docs` is CodeRabbit's
*highest*-delivery context (7/18). Rules are proposed by reasoning and
kept only if the metrics support them.

## 8. First test-metrics readout (2026-10-23, 60 PRs / 92 cycles)

| Provider | Cycles | Required | Delivered | Rate | Cooldown cycles | Median latency | Verdicts | Issue comments | Review comments |
|---|---|---|---|---|---|---|---|---|---|
| coderabbit | 92 | 92 | 16 | 0.174 | 31 | 475.5s | CHANGES_REQUESTED 23, COMMENTED 1, APPROVED 1 | 133 | 115 |
| ecc | 0 (untracked) | 0 | — | — | — | — | — | 722 | 0 |
| qodo | 0 (untracked) | 0 | — | — | — | — | — | 48 | 0 |

Reading: a third of cycles hit CodeRabbit's rate limit (cooldown is the
dominant non-delivery cause, i.e. quota cadence, not refusal); delivery
is strictly SHA-bound by definition, so the rate is a floor. ECC is the
volume leader by an order of magnitude while delivering zero formal
reviews — comment-only by vendor design, and exactly the kind of fact
the map exists to keep visible. Bot contexts are thin in this window
(3 cycles; the recently-updated window is dominated by owner-PAT fleet
PRs) and will thicken now that every cycle records its context.

## 9. Adaptation log

- **2026-10-23** — JIT v1 landed: context capture (§3), policy rules
  (§7), variable baselines (§6), `.coderabbit.yaml` gains
  `path_filters` (generated tree excluded) + `path_instructions`
  (workflows / docs / deepcli) + explicit
  `auto_pause_after_reviewed_commits: 5`; collector + weekly refresh
  workflow; first metrics map (§8). Owner review of test metrics is the
  gate for the next adaptation round.
- **2026-10-24** — Round 2 (owner-selected A+B+C after reviewing the
  widened 150-PR map: delivery rate stable at ~0.173 across windows,
  cooldown ~35% of cycles, bot contexts 10 required / 0 delivered over
  6 keys, Devin + Qodo first tracked, ECC 964 comments / 0 reviews):
  (A) cooldown-aware triggering (§7 rule 4); (B) author-class rollups
  in the map + rollup evaluation in the zero-delivery rule (§7 rule
  2b); (C) ECC findings metric (§5). No thresholds changed; no new
  exemptions for user contexts — none qualified. Also fixed: the
  collector workflow's permissions were read-only, so its first
  dispatched run (2026-10-24) failed at the refresh-PR step after a
  successful collect; the job now carries contents + pull-requests
  write, which the push + PR-create steps require.
