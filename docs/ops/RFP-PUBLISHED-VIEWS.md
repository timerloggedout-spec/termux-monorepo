# RFP Published Views

## Purpose

Expose method-aware campaign views through the existing Tribute GitHub Pages PWA publisher. The view selector changes the presentation of one normalized view model assembled from the method catalogue and the existing DoE evidence snapshot; it does not fork campaign identity, run evidence, or release provenance.

## Publisher integration

The canonical static artifact root is `apps/tribute-dashboard/`. The existing `.github/workflows/tribute-dashboard-deploy.yml` copies that complete tree into the Tribute Pages subtree, runs `scripts/build_dashboard_manifest.py`, and publishes the version-stamped artifact. A new top-level HTML page is therefore registered in the generated `version-manifest.json` and receives the shared `versioning.js` navigation/version header during publication.

The publisher retains the existing release identity contract: `MAJOR.MINOR.PATCH+<12-character-source-SHA>`, channel, full source SHA, source ref, build timestamp, stable page IDs, and per-page SHA-256. Preview and production remain isolated under the existing publisher workflow.

## View contract

`data/experiment-view-feed.json` is the normalized presentation feed. The current seed uses `rfp-published-views/v1` and separates:

- `methods`: versioned pipeline methods and their classifications;
- `phases`: canonical governance phase catalogue;
- `design_classes`: design taxonomy and implementation status;
- `campaigns`, `workstreams`, `experiments`, `runs`: campaign-specific records. A workstream carries a stable `id`, optional `method_id`, lifecycle `state`, `dependencies[]`, and source-backed `start` / `end` dates for schedule projection.

The view catalogue seed intentionally contains no campaign, workstream, experiment, or per-run records. The page joins it with the existing `apps/tribute-dashboard/data/doe-feed.json` snapshot (`dashboard-surface-feed/v1`, surface `doe`), generated by `scripts/dashboards/surface_feeds.py`. Campaign state, recorded run totals, design metadata, and campaign-level result summaries come from that existing feed. The collector remains the data producer; this page adds no duplicate ledger or network collector. Campaigns merge by stable `campaign_id` (or `id` where supplied): the DoE snapshot provides base evidence fields, then an explicit view-feed record overrides matching fields and adds method-specific attribution. New records from either source remain in the merged list. Individual per-run receipts are not synthesized from campaign totals. RFP-specific campaign and workstream records remain to be connected to this model. Workstream schedule dates are rendered only when an authoritative workstream record supplies them; the existing DoE snapshot does not supply those dates.

## Native views

- Overview: method and campaign inventory.
- Gantt / schedule: method-linked workstream dates; calendar bars appear only when authoritative `start` and `end` fields exist.
- Dependency graph: workstream prerequisites; canonical phase sequence remains a separate fallback.
- Admission board: lifecycle-state columns.
- Design matrix: DoE design classes with generator availability.
- Results: campaign-level result summaries and arm metrics present in the DoE feed; per-run evidence remains a separate source.
- Adaptive flow: discovery, screening, expansion, replication, validation, and promotion/cull.
- 13-phase map: canonical governance order.

Each view is a projection of the same feed. Selecting a method filters campaign, workstream, experiment, and run records by `method_id`; absent method assignment remains visible as shared context.

## Evidence and authority boundaries

The feeds are descriptive snapshots. A method catalogue entry does not establish admission, execution, validated outcomes, or production routing. A design class marked candidate or skill-named does not imply an implemented generator. DoE campaign run totals remain campaign-level counts; the page labels them as such and renders result summaries only when present in the source. DoE campaigns without an explicit `method_id` remain shared family evidence rather than being attributed to an RFP pipeline version. External due dates and schedule fields require source provenance in the upstream campaign/workstream record.

## Validation

Run:

```sh
python3 -m pytest tests/test_experiment_published_views.py -q
node tests/test_experiment_published_views.cjs
node --check apps/tribute-dashboard/experiment-views.js
python3 scripts/build_dashboard_manifest.py --root <artifact-dir> --channel preview --source-ref <ref> --source-sha <sha>
```

The normal preview workflow must verify the generated manifest, preview URL, page navigation, and browser behavior before merge. Production publication remains the existing serialized Tribute Pages release path. The focused validation workflow runs one non-scheduled job per matching pull-request update; merged changes use the existing serialized publisher rather than a second master-push validation job.
