# B3 — Read-Only Agentic Operations Pilot

**Status:** Implemented as a bounded pilot on `fix/ar01-automation-baseline`; pending pull-request review and runtime credentials.  
**Ledger item:** X-05 / B3  
**Source:** `.github/workflows/agentic-repository-operations-report.md`  
**Generated lock workflow:** `.github/workflows/agentic-repository-operations-report.lock.yml`

The B3 pilot provides one weekly, advisory repository-operations report. The agent can read only issue and pull-request metadata; it has no write-capable repository permission. It can emit either a `noop` record or exactly one structured `create_issue` request. A compiler-generated, separate safe-output job is the only job with `issues: write`; it cannot write code, create a pull request, comment, dispatch a workflow, change labels, or change repository state.

> The source is Markdown, but the executable artifact is the reviewed `.lock.yml` file. The lock file is regenerated by `gh aw compile` and SHA-pins its generated Actions dependencies.

| Surface | Bounded control |
|---|---|
| Trigger | Weekly Monday schedule plus `workflow_dispatch` for a controlled trial; no issue, comment, pull-request, push, or repository-dispatch trigger. |
| Agent permissions | `contents: read`, `issues: read`, and `pull-requests: read` only. The compiled workflow has `permissions: {}` at scope and explicit read scopes in the agent job. |
| Tools | GitHub issues and pull requests only. The source prohibits browser, shell, edit, network, MCP, and write-capable GitHub tools. |
| Output | `create_issue` only, `max: 1`, title prefix `[agentic-ops]`, title de-duplication, and an allowed GitHub-reference set of `[]`; `noop` remains the non-writing system output. |
| AI cost | Main agent: maximum 40 AI Credits per run, 80 per 24 hours, four turns, and eight minutes. Threat detection: a separate 20-AI-Credit cap. |
| Injection boundary | All user-authored repository content is explicitly untrusted. The report must not reproduce issue/comment body text or follow embedded instructions. Compiler-generated threat detection runs before the safe-output job. |
| Output contract | The report schema requires a dated fixed-format title and five ordered headings: Scope, Observations, Evidence, Risk flags, and Cost guardrail. The body is limited to 6,000 characters. |
| Failure handling | Automated failed-job issue reporting is disabled. Threat detection failure prevents the safe-output job; the pilot produces no side-effecting fallback. |

## Compiled Lock Review

The lock file generated by `gh aw` v0.86.2 has scope-level `permissions: {}`. Its `agent` job requests only the three read scopes. Its `safe_outputs` job requests only `issues: write`, and the generated handler configuration permits `create_issue` at `max: 1` plus non-writing system records. The agent job receives no direct `issues: write`, `pull-requests: write`, or `contents: write` permission.

The compiled lock does include the GitHub-native runtime mechanics required to obtain repository context, cache daily AI-credit accounting, execute the selected model, run threat detection, and process the safe-output artifact. Those mechanics are compiler-owned and SHA-pinned. They are not a grant of source-level code-write capability. Every future source or compiler upgrade must regenerate the lock file and repeat the lock review.

## Test Corpus and Promotion Boundary

The companion deterministic contract test validates the source/lock permission boundaries, configured credit caps, allowed safe output, fixture trigger allowlist, prompt-injection corpus, and sample output schema. The fixture corpus intentionally includes instruction-override, credential-exfiltration, link-following, direct-write, and scope-expansion text; it must be treated as data only.

This pilot is not B4. It does not create code, commits, pull requests, comments, labels, assignments, dispatches, or external requests. B4 remains separately blocked pending accepted write-authority and event-provenance tests. B5 remains unimplemented because there is no concrete external service-capacity use case that justifies a typed dispatch envelope.
