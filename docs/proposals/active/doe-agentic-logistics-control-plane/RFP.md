## 1. Executive request

Evaluate and implement, in gated phases, a composable agent-engineering and decision-control ecosystem that can plan logistics/workflow dependencies, execute stateful agent workflows, and optimize eligible no-cost inference capacity using control-systems methods. The target is an evidence-producing system governed by the existing DoE, ATES, provider admission, identity, QDesk and Observatory contracts—not a new model router or autonomous spending mechanism.

The user already maintains a LangChain fork and a LangGraph integration is being developed concurrently. There are also PDDL air-cargo, multi-agent logistics and freight-workflow repositories in the account. This RFP turns those assets into a controlled research and implementation program.

## 4. Target architecture

### A. Framework and agent layer

- **LangChain** provides composable model, embedding, tool, retriever, document and provider-integration interfaces.
- **LangGraph** provides explicit state, conditional/cyclic transitions, fan-out/aggregation and checkpointed graph orchestration where those capabilities are needed.
- **Deep Agents** is an alternative harness where planning, filesystem/context handling, skills and subagent delegation outweigh hand-authored graph control.
- **Temporal** remains the durable cross-process/workflow boundary where retry, scheduling, worker recovery and long-running execution are required. LangGraph can run inside a Temporal Activity; neither replaces the other.
- **LangSmith** can be an optional trace/evaluation/deployment surface. The repository's existing telemetry/evidence contract remains neutral and canonical.
- **Provider integrations and MCP adapters** remain behind current provider dispatch/capability contracts. Provider identity is never inferred from a framework class name.

Select the least complex tool for each workflow. Linear CLI/tool work should not be forced into a graph. Graphs should expose typed state, explicit reducers, idempotent nodes and testable transition boundaries.

### B. Symbolic planning and logistics layer

Use **PDDL** for domain facts, action preconditions/effects, goal states and hard precedence. Begin with the owned Air Cargo domain as an educational fixture and develop a separate, small fleet-dispatch domain only after its state/actions are precisely defined.

Do not force every optimization problem into classical PDDL:

- **Unified Planning** is a candidate for consistent problem construction, PDDL parsing/serialization and comparison of installed planner engines.
- **Fast Downward** is a candidate classical planner for supported PDDL fragments; its supported language subset must be checked against each domain. Do not assume it provides general numeric/temporal scheduling.
- **OR-Tools CP-SAT / Routing** is a candidate for numeric capacities, assignment, time windows, vehicle-routing and scheduling constraints.
- **PDDLStream** is exploratory for problems requiring sampling procedures or task-and-motion planning; it is not a dependency for the initial pilot.

The division is deliberate: PDDL captures symbolic feasibility and action order; CP-SAT/Routing handles resource and time-window optimization; the runtime controller responds to changing queue and endpoint conditions. The project must not create another cron, scheduler or execution authority.

### C. Control-systems layer for free inference

Treat each configured provider × model × endpoint × account route as an observed plant instance, not as a string in a public catalog.

**Observable state (when actually available):** queue depth and age; arrival/completion rates; in-flight concurrency; success/error/timeout/429 rates; latency distributions (especially p50/p95); endpoint-health observation time; quota headroom; reset boundary/timezone; exact account/model/route entitlement evidence; cost class; and configured-instance provenance.

**Bounded control actions (proposal only):** admission limit, per-arm concurrency cap, dispatch pacing, cooldown/backoff and shadow allocation. No key rotation, account creation, quota changes, policy bypass or provider selection by an unverified catalog record.

**Disturbances:** arrival bursts, provider degradation/outage, rate limiting, network jitter, shared quota contention and reset-window transitions.

**Candidate policies to compare:** fixed baseline; threshold + hysteresis with bounded backpressure; conservative PI/PID-style concurrency control with saturation and anti-windup; and finite-horizon MPC/constraint-based allocation where the state estimate and constraints are sufficiently grounded. These are candidate treatments—not an endorsement of a particular controller. Avoid noisy route oscillation, over-correction, hidden queue growth and retries that amplify load.

**Fail-closed eligibility invariant:** a provider arm is excluded/deferred unless its exact configured instance has an approved invoke route, current successful availability evidence from the relevant execution environment, authoritative no-cost entitlement/terms for the account and model, fresh usable quota headroom with source/time/reset zone, approved data classification, and complete provenance. Unknown or stale means not eligible. Paid fallback is forbidden.

Issue #5160 owns provider-pool and autoQuotaCadence implementation, and is currently blocked on prerequisite integration/external execution. This RFP may design and simulate around that contract; it must not duplicate or bypass it.

## 5. DoE design and measurement plan

Register treatments before execution in the existing DoE family. Keep exploratory/simulation and live provider cohorts separate.

Candidate factors for a staged design:

1. Planning treatment: declared FIFO/dependency baseline; PDDL planner; CP-SAT/OR-Tools assignment.
2. Control treatment: fixed caps; threshold/hysteresis; bounded PI/PID; constrained receding-horizon policy.
3. Workload class: independent tasks; dependency DAG; parallel fan-out; synthetic logistics/capacity workload.
4. Plant condition: healthy/fresh; low-but-positive headroom; stale/unknown quota; reset boundary; provider degradation/429.
5. Retry/backpressure treatment: bounded retry with jitter; deferred admission; no retry.
6. Execution topology: direct linear path; LangGraph graph; Temporal-wrapped graph where durable execution is needed.

The DoE expert must choose a tractable design, factors/levels, blocking and run budget. Use the repository's existing design generators where appropriate; do not assume every factor combination is needed. Repeated executions of one task are repeated measures, not independent task replication. Preserve failed, censored, skipped, blocked and negative observations.

**Primary outcome:** correctness and safe goal attainment, adjudicated by an independent deterministic verifier.  
**Secondary outcomes:** successful completion rate, invalid/unsafe action count (hard zero), deadline miss, queue wait, p50/p95 latency, throughput, retries, provider errors, cost class, quota deferrals, recovery behavior, integration effort and human intervention.  
**Quality rule:** throughput or ATES never overrides correctness, safety, privacy, quota eligibility or independent evidence. No statistical-significance or causal claim without a stated estimand, suitable replication/power rationale, uncertainty and diagnostics.

### Free-inference endpoint tournament — governing design

The machine-readable execution order is [`FREE-INFERENCE-TOURNAMENT-ORDER.yml`](FREE-INFERENCE-TOURNAMENT-ORDER.yml). It is the implementation sequence for DPLC-004 and DPLC-005, not a new provider or queue registry.

**Population and arm identity.** The tournament unit is an exact provider family × exact model ID × endpoint/route × protocol × account-scope reference × configured-instance identity. Provider records, endpoint records, configured instances and dispatch harnesses are different denominators. The provider participation index (#5134) and the provider/model inference-pool repair (#5160) own the endpoint population. The build-dispatch harness arm registry (#5151) and admitted build executor (#5176) are not substituted for that inference population.

**Existing DoE campaign.** Extend the existing `util-1-provider-rotation` campaign with a versioned, separately identified inference cohort. Do not create a duplicate campaign and do not pool the new cohort with the existing live build-task observations. The generic `routed-dispatch` campaign remains observational intake unless a dispatch is assigned under the amended pre-registered design. The DoE specialist must confirm the cohort is valid under the campaign's live-production basis before it is admitted.

**Live-first evidence.** Offline simulation is required to test controller safety and logistics behavior, but simulation results are not live experiment observations. Designed endpoint comparisons must be integrated into the existing production dispatch flow, use public/sanitized task data, and emit one EXPERIMENT record per real dispatched/executed request. A catalog row, smoke check, model listing, proxy test or successful workflow is not a scored tournament observation.

**Replication and stopping.** Apply DoE-FAMILY rules 5–9. The automation must be part of the admitted design. Each trigger accrues auditable sets of three with fresh auto-selected configured instances, `instance_key`, `set_index` and `cumulative_n`; cap at 12 per trigger or the tighter cohort/window/budget bound. A 2–1 split or spread-in-noise buys one additional set; a cap reached without a conclusion is INCONCLUSIVE. Weight-bearing claims require the relevant stratum and the repository's class-specific significance standard.

**Separate endpoint and manager effects.** The first cohort holds manager policy fixed and estimates endpoint differences. A later manager-policy comparison may use the existing `manager.tournament.v1` schema and contract over a frozen task cohort/environment/budget. Do not confound endpoint and manager treatments in one unidentifiable comparison. Manager activity volume is not a quality outcome.

**Eligibility is a dispatch-time gate.** An endpoint is eligible only with current exact-route availability from the actual execution environment, authoritative account/model no-cost entitlement and terms, usable quota/headroom with source and observation time, approved data classification, explicit stop switch and complete provenance. Unknown/stale means defer. Promotional credits, prepaid balances, trials, catalog-only evidence, credential presence and `:free` suffixes do not establish no-cost eligibility. No paid fallback, automatic retry, alternate model, cookie/HAR route or account mutation is permitted.

**Issue-open provider invocation is a pre-tournament safety blocker.** The dispatch observation for #5195 records an issue-open listener invoking OpenRouter before QUE admission: the request selected `google/gemma-4-31b-it:free`, returned HTTP 429, and the independent QUE admission attempt deferred because the queue picture could not be collected. This was not a designed observation, not successful inference, and not an authorized tournament run. The generic issue-open provider-bearing path must be gated behind QUE admission or a separately authorized explicit command, with regression tests proving that deferred/unadmitted issues cause no provider request. The observed 429 is retained as a control-gap event and excluded from tournament scoring.

**Current blockers are retained, not papered over.** PR #5134 reports 98 model-lane records with all 98 free-eligibility values unknown; it is not merged at this order's preparation. Issue #5160 records the pool/cadence repair as blocked on prerequisite integration and external execution access. Therefore the first permitted work is offline reconciliation, simulation, design amendment and deterministic tests. No live endpoint tournament is currently authorized.

2. Is PDDL limited to symbolic planning while numeric/time-window optimization belongs to a suitable constraint solver?
3. Are the endpoint state, control action and disturbance models measurable and safe?
4. Are free-entitlement and quota requirements strict enough to prevent accidental paid or unauthorized inference?
5. Are DoE factors, units, strata, sample semantics, outcomes and stopping rules adequate?
6. Are #5045, #5145/#5146, #5160, #5136/#5183/#5176/#4979 and #5189 correctly reused as existing owners?
