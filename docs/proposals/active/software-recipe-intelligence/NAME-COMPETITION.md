# Naming Competition — Versioned Candidate Arms

**Experiment ID:** NAME-DOE-001  
**Status:** design ready for review; not preregistered, not run, no winner  
**Shared capability descriptor:** Software Recipe Intelligence  
**Model identifier:** SRM — Software Recipe Model  
**Project/system identity:** unassigned

## 1. Decision principle

Names are competing versions of the same proposed capability, not separate products and not separate architectures. Each candidate is an identity treatment over one frozen capability brief. No candidate may change the scope, architecture, permissions, roadmap, or technical implementation.

This avoids a naming contest becoming an accidental product fork. Candidate arms compete on semantic accuracy, memorability, pronunciation, discoverability, repository fit, and collision risk. The capability specification remains invariant across arms.

SRI remains a useful descriptive phrase and a benchmark arm, but not the default public acronym. The SRI International / Stanford Research Institute association and its Siri-origin history create a material identity collision.

## 3. Frozen capability brief shared by every arm

The capability describes software, algorithm, API, library, integration, workflow, agent, agent-team, operational, research, and recovery recipes as versioned, evidence-bearing structures. A recipe captures intent, ingredients, preconditions, ordered procedures, environment, outputs, evaluation contracts, provenance, lineage, and relationships to existing systems.

It discovers, classifies, compares, retrieves, composes, evaluates, and helps evolve software capabilities. It does not create a second Brain, Grimoire, orchestration plane, replay engine, graph, memory store, experiment ledger, registry, or promotion authority. It is advisory until separately admitted. Execution and promotion remain under existing owners.

## 4. Experimental protocol

### Phase N0 — registry and collision baseline

- Freeze the shared capability brief and candidate expansions.
- Record exact spellings, expansions, aliases, pronunciation hypotheses, semantic promise, and intended audience.
- Search repository identities, GitHub repositories, crates.io, npm, PyPI, domains, public company/product sources, and trademark databases.
- Record evidence URL, access date, source class, exact/near/phonetic/semantic match, category overlap, jurisdiction/class where available, and uncertainty.
- Distinguish current use, historical use, abandoned filings, active applications, registrations, and unrelated-category matches.
- Do not infer legal clearance from absence of search results.

### Phase N1 — blind semantic evaluation

Give independent reviewers the same short capability description and one candidate name at a time, with arm IDs randomized and expansions hidden in the first pass. Ask reviewers to infer:
- what the system does;
- whether it sounds like a model, tool, platform, research method, or organization;
- expected scope and authority;
- likely domain (software engineering versus cooking, finance, research institute, etc.);
- confidence in spelling and pronunciation after hearing it once.

Then reveal the expansion and measure semantic fit, surprise, confusion, and recall.

### Phase N2 — retrieval and discoverability

Measure exact-name search precision, top-result relevance, repository/package namespace conflicts, acronym ambiguity, and ability to find the intended project from the name alone. Record queries, engine, locale, timestamp, and result set. Do not treat web search ranking as trademark evidence.

### Phase N3 — repository and ecosystem fit

Check naming consistency with existing repository systems and naming governance. Evaluate package namespace feasibility separately for Rust crates, npm packages, PyPI distributions, GitHub repositories, and internal module identifiers. Preserve existing identities such as GRIMOIRE, MOSAIC, SIGLARY, RUNE, Repo Replay, Commit Replay, and Brain systems.

### Phase N4 — decision and retention

Produce an evidence-backed comparison. The result may be:
- select one candidate for formal Name Forge / governance review;
- retain multiple candidates pending better evidence;
- reject all candidates and generate a new cohort;
- retain a descriptive project identity without a branded acronym.

No automatic renaming, package/repository creation, domain reservation, trademark filing, or identity migration is authorized by this experiment.

## 5. Scoring model

Score each non-gated dimension from 0–5 with an explicit rubric and evidence:
- semantic fidelity and scope accuracy;
- distinctiveness within software/AI/developer tooling;
- pronunciation and spelling reliability;
- recall after delay;
- search precision and discoverability;
- extensibility as the capability grows;
- compatibility with repository naming and notation governance;
- cross-locale pronunciation and unintended meanings;
- user/reviewer preference.

Collision risk is assessed separately as a gate, not averaged away. A severe same-category identity collision can disqualify a candidate regardless of its popularity score. Do not collapse all dimensions into a single score until weights and aggregation are preregistered. Report confidence intervals, disagreement, and missing values.

## 6. Controls and bias prevention

- SRI and RACE are negative controls for known acronym ambiguity/genericity.
- RAXI, BRACE and TARSIER are collision controls; do not rehabilitate them by changing capitalization or expansion.
- Randomize presentation order and hide expansions in the first semantic pass.
- Keep the capability brief, audience, questions, and scoring rubric identical.
- Separate candidate generation from candidate scoring.
- Preserve rejected names and reasons; do not silently recycle them.
- Do not let an acronym's expansion dictate technical architecture.
- No candidate receives a higher score because it resembles an existing repository term.

## 7. Acceptance gates

A candidate can advance only if:
1. no unresolved severe collision exists in the relevant software/AI/developer-tool categories;
2. repository and package namespace checks are complete enough for the intended use;
3. semantic interpretation is consistent with the frozen capability brief;
4. pronunciation, spelling, recall, and discoverability are acceptable;
5. existing repository naming authorities have reviewed it;
6. the decision record explains uncertainty and rejected alternatives.

Trademark counsel / formal clearance remains separate from this engineering experiment.

## 8. Current outcome

**No winner. No candidate is cleared. No public identity is issued.**

RIE, RISE, and RIME form the first active candidate cohort, with deliberately different collision profiles. SRI, RACE, RAXI, BRACE and TARSIER are controls or exclusions, not fallback winners. The next step is to complete N0 evidence capture and then run N1/N2 using a frozen rubric.
