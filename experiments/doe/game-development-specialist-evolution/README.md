# Game Development Specialist Evolution — DoE Campaign Candidate

<badge-placeholder>

**Status: proposed / not admitted.** This directory is a design proposal, not an active campaign, a populated specialist pool, or evidence of any completed experiment.

## Purpose

Compare generalist and context-specialized game-development instances across toolchain depth, orchestration topology and verification strength. Improve the specialist population by measured outcomes, then propagate only reviewed prompt/tool/workflow slices into a new generation.

## Admission requirements

Before any designed dispatch:
1. DoE oversight reviews and admits `DESIGN.json`.
2. The task suite, block definitions, factor levels, selection fraction, minimum sample, confidence method, stopping rule and quota budget are locked.
3. The baseline and candidate configured instances have stable identities and exact prompt/tool hashes.
4. Each task has a target record, authorization basis, requirement contract and independent reviewer.
5. Every executed run emits one record conforming to `docs/ops/corpus/EXPERIMENT.schema.json`.

No run records are present. No candidate has been promoted or culled by this proposal.

## Record layout

- `DESIGN.json`: pre-registered hypothesis, factors, blocks, outcomes, constraints and decision rule.
- `records/`: append-only one-record-per-executed-observation evidence.
- `SUMMARY.json`: produced only after observations exist; never hand-filled with invented results.
- `README.md`: operating notes and admission state.

The DoE family admission rule applies: a proposal alone does not become a campaign member; committed design plus run evidence is required.
