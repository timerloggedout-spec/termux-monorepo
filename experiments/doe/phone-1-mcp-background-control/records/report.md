# Phone MCP and MCP-Based Background Phone Control — Research Report

*Researched 2026-11-04. “Verified live” = page fetched and read in this session. “Index” = search-index snippet only. Vendor/product claims are labelled as claims; they were not independently tested on a device.*

## Summary

**There is no single product called “Phone MCP.” At least five different projects/products use that exact name, and the ad the user saw cannot be pinned down from the description alone.** The candidates, in order of how likely an *advertised, consumer-facing* product is:

1. **Premex AB “Phone MCP: AI Assistant Server”** (Google Play, phonemcp.ai) — the only one literally sold in an app store under the exact name “Phone MCP.” It turns the phone *itself* into an MCP server for data tools (files, camera, sensors, contacts, location, SMS drafts) — it does **not**, in its shipped tool list, do general tap/swipe phone control.
2. **PhoneMCP at phone-mcp.com** — a commercial, ad-style landing page for AI business texting from your own number. SMS only; no UI control.
3. **AGI Inc “AGI Agentic Phone MCP”** (platform.agi.tech, launched 2026-08-06) — not named “Phone MCP” but marketed almost exactly as the ad genre suggests: “Your Android phone is now an MCP server… your agent gets the screen: it sees it, taps, and types.” Cloud-relayed, on-device Accessibility agent, foreground/visible execution.
4. **hao-cyber “Phone MCP Plugin”** (PyPI `uvx phone-mcp`) — the best-known open-source project under the exact name in MCP directories; host-side ADB control including calls/SMS.
5. **viandwi24/phone-mcp** — a small open-source project that is, architecturally, *exactly what the user is building*: a sideloaded on-device APK (foreground service + Accessibility + MediaProjection) holding a persistent WebSocket to a self-hosted broker, driven by a local stdio MCP server. No ADB, no root.

**The single most important technical finding for the builder:** “Controls a phone in the background” means three different things in this market, and only one of them is true concurrent background operation:

| Meaning of “background” | Who actually does it | How |
|---|---|---|
| **A. Service stays connected while screen is off** (phone idle, nobody using it) | viandwi24/phone-mcp, Premex, PhonePi, htekdev, ScreenMCP | Foreground service + battery-optimisation exemption; tools wake the screen on demand. A PIN/pattern/biometric lock still blocks control. |
| **B. Agent works on a hidden second display while the user uses the main screen** | **Mika** (open source, Oct 2026) — the only clear example found | Shell-identity helper process (started via wireless-debugging pairing) creates a **VirtualDisplay**, launches apps there, drives them via Accessibility/OCR/vision. Android 14+ recommended because the background display gets independent focus. |
| **C. Marketing “background” = foreground mirroring/automation, just unattended or with the physical screen dark** | mobile-mcp, Android-MCP, DroidMind, scrcpy/scrcpy-mcp, AGI, Melaya, Mobilerun Portal, Open-AutoGLM | ADB `input`/`screencap`/`uiautomator dump`, or Accessibility on the *active* window, or scrcpy (which can turn the physical screen off while mirroring — the app is still foreground). If the user picks up the phone, agent and user fight over one display. |

No system found bypasses a credential lock screen, `FLAG_SECURE` screens (banking/DRM/password), or biometric/CAPTCHA hand-off — every credible project explicitly hands those back to the human.

**Pattern summary:** the field splits cleanly into (i) **host-side ADB/Xcode servers** (nothing or almost nothing installed on the phone; the host must be present), (ii) **phone-as-toolbox servers** (on-device, direct APIs for SMS/contacts/sensors; no UI control), and (iii) **on-device UI agents** (Accessibility ± MediaProjection ± shell helper, outbound connection to a broker/cloud; the only group that works away from a host computer).

### 3. What “controls a phone in the background” technically means

#### 3.1 The five control primitives (and what each can/cannot do)

**ADB (host → phone, shell UID 2000).** The host's authorised RSA key gets a shell that is pre-granted `INJECT_EVENTS`. Primitives used by nearly every host-side MCP: `input tap|swipe|keyevent|text`, `exec-out screencap`, `uiautomator dump`, `am`/`pm`/`dumpsys`, and full `adb shell`. Limits that matter: `input` is **single-touch only** (no pinch); `input text` is effectively printable-ASCII (`%s` for spaces, emoji/non-ASCII break it); each `input` call spawns a process (hundreds of ms); `uiautomator dump` takes ~1–2.5 s on slow hardware, **fails when the UI never goes idle and returns a null root when the screen is off**; taps *do* land on the keyguard (you can swipe up / type a PIN — which is exactly why several projects deliberately refuse to), but **nothing bypasses the credential check itself, biometrics, or the pre-boot encrypted state**; `FLAG_SECURE` windows return black/empty. Sources: Android-control survey and PocketAgent limits docs (index): https://github.com/shenxyt/iphone-ian/blob/HEAD/research/android-control-survey.md , https://github.com/p0tfur/pocketagent/blob/HEAD/docs/capabilities-and-limitations.md . ADB works “in the background” only in sense A/C: the *display it drives is the foreground display*.

**Android AccessibilityService (on-device).** A user-enabled service that runs in the background and receives events for the *active* window: `rootInActiveWindow` node tree, node actions (click/set-text/scroll), `dispatchGesture()` (arbitrary strokes, treated by the system as real touches), `performGlobalAction()` (Back/Home/Recents/Notifications/Lock/…), and — API 30+ — `takeScreenshot()` with no MediaProjection consent dialog. Official reference: https://developer.android.com/reference/android/accessibilityservice/AccessibilityService (index). This is the workhorse of AGI, Melaya, ScreenMCP, Mobilerun Portal, viandwi24. **Crucially, by itself it still operates the foreground display** — concurrent use requires pairing it with a virtual display (§3.2). Costs: user must enable it in Settings; **sideloaded apps on Android 13+ hit “Restricted settings”** and need *App info → ⋮ → Allow restricted settings* first (documented by viandwi24, Melaya and Mobilerun alike); OEM battery managers kill it unless exempted.

**UI Automator (host/test-side).** The instrumentation framework behind `uiautomator dump` and Appium's Android driver. Same tree as Accessibility (it rides the accessibility subsystem), same idle/idle-timeout failure modes, but requires a test harness/ADB session — it's a *foreground-display, host-attached* technique, not an on-device background service.

**scrcpy (Genymobile).** Pushes a server over ADB that captures the display via a virtual display + MediaCodec and injects input. Two facts cut through marketing: (1) `scrcpy --turn-screen-off` lets the *physical* screen go dark while mirroring/control continues — the controlled display is still the foreground one (https://github.com/Genymobile/scrcpy/blob/master/doc/device.md, index); (2) newer scrcpy `--new-display` creates a genuine virtual display — the seed of the Mika pattern. No root; still needs USB debugging authorised.

**Shizuku / shell-identity helpers (on-device privilege bridge).** Shizuku starts a long-lived process via root, PC `adb`, or on-device wireless-debugging pairing (Android 11+); client apps then call system Binder APIs **as shell (UID 2000) or root (UID 0)**, with per-app user consent. It is *not* root in ADB mode, cannot read other apps' private data files, and an unrooted Shizuku **must be restarted after every reboot**. This — or the equivalent self-rolled `app_process` helper — is what unlocks the things a normal app cannot do: creating/owning a VirtualDisplay, launching activities onto it (`ActivityOptions.setLaunchDisplayId`), reliable screenshots/input at shell level. Mika's helper is this pattern: “a helper process running with Android's shell identity, started through debugging access… creates a virtual display” (architecture summary, index: https://aiidelist.com/blog/mika-ai-phone-agent-android-mcp-guide ; setup behaviour from Mika README, verified live).

**Appium / WebDriverAgent (iOS, and Android via UiAutomator2).** On iOS, WDA is an XCTest bundle whose never-returning test hosts an HTTP server on the device; the host drives it over a usbmux/go-ios tunnel. It is the *only* sanctioned full-UI path on a real iPhone, and it is a **developer/test construct**: signed with your provisioning profile, Developer Mode on, Mac-paired, and it controls the foreground app while the test session lives. mobile-mcp's newer releases swap WDA for their own DeviceKit XCUITest agent — same fundamental model (index: mobile-mcp CHANGELOG).

**Root.** Removes most of the above ceilings (start helpers at boot, read app data, bypass some OEM kills) at the cost of: no Play Integrity/banking reliability, OTA/security-patch pain, and a much larger blast radius if the agent/broker is compromised. **No surveyed consumer MCP product requires root**; all treat “no root” as a headline feature. Root-only/research tools (e.g. Frida-based MCP proofs of concept) exist for security testing, not personal automation.

#### 3.2 The three “background” meanings, mapped to evidence

- **Screen off, phone idle (sense A) — real, with a lock caveat.** viandwi24 documents it most honestly (README, verified live): connection survives screen-off with battery optimisation disabled; “every screen tool wakes the phone on demand… a swipe/none lock is dismissed… after 30 s without commands the screen is locked again (only if the agent woke it — it never locks a phone someone is using). **A PIN/pattern/biometric lock cannot be unlocked remotely — that is an Android guarantee, and this project does not try to work around it.**” Its unattended-phone advice: set screen lock to None/Swipe *on a dedicated device only*. MediaProjection-based capture adds its own ceiling: consent is per-session on Android 15+, and Android 15 QPR1 stops projection when the device locks (secondary summaries of Android behaviour changes, index) — one reason Accessibility `takeScreenshot()` (API 30+) is preferable where available.
- **User actively using the phone (sense B) — only via a second display.** Mika (README, verified live): “Opens apps, taps, types and scrolls on a separate background screen while you use your phone as usual.” Requirements from the same README: app control needs Android 12+, **Android 14+ recommended because “the background screen has its own focus, so it doesn't get in the way of your typing on the main screen”**; on 12–13 background work can interfere with foreground focus. Multi-window/virtual-display caveats a builder must expect: some apps refuse secondary displays, assume the default display for camera/DRM/FLAG_SECURE, or break on focus/audio routing; the agent's display has no physical user, so incoming calls, permission dialogs and system UI still surface on the *main* display.
- **Foreground mirroring called “background” (sense C).** AGI: “Tasks run on a real phone through accessibility APIs, **visible on screen as they happen**” (docs, verified live). Melaya: visible working overlay, “show control, not a mirror.” mobile-mcp/Android-MCP/DroidMind/Open-AutoGLM: the agent literally is the foreground user. If the user touches the phone mid-task, focus theft and interleaved input are expected failure modes, not edge cases.

#### 3.3 iOS limits (why every “iOS too” claim needs interrogation)
- **No third-party Accessibility equivalent.** ScreenMCP's own iOS feasibility analysis states it plainly: iOS third-party apps cannot take system-wide screenshots, read other apps' UI trees, or inject taps — “none of these capabilities are available to third-party apps” through public APIs (index, via rebrand commit diff). Melaya's FAQ agrees: “iOS does not expose Android-style Accessibility control to third-party apps. Any iOS version would need a separate Shortcuts or App Intents design” (verified live).
- Therefore real-iPhone control = **WDA/DeviceKit test runner** (Mac, Xcode signing, Developer Mode, pairing, tunnel; foreground, session-bound), **simulator** (not a phone), **cloud device** (someone else's phone, Mobilerun/BrowserStack), or **iPhone Mirroring** — Apple's own Mac feature: iPhone must be **locked**, near the Mac, same Apple Account with 2FA, macOS Sequoia 15+/iOS 18+, one Mac ↔ one iPhone, unavailable in the EU (Apple Support: https://support.apple.com/en-lb/120421, index). Mirroring is the one case where a *locked* phone is controllable — because the user authenticated to Apple, not because automation bypassed the lock.
- SMS-from-iPhone products (e.g. Sparetext, textbee-style gateways) cheat differently: a **Mac relay over Text Message Forwarding** or the Android default-SMS-app role — telephony via an OS-sanctioned side door, not UI control (index).

### 5. Security and permission model

**What the MCP client/host actually gains — by pattern:**
- **Host-ADB pattern:** whoever holds the authorised ADB key effectively holds the phone *as the shell user*: install/uninstall apps, grant permissions, read world-readable storage and logs, inject input anywhere, run any `adb shell` command the server exposes. android-mcp-server and DroidMind expose shell explicitly (DroidMind at least validates it); mobile-mcp exposes install/clear-data/log tools. There is no per-app scoping in ADB — scoping, if any, is policy in the server.
- **On-device Accessibility pattern:** the client gains *the user's eyes and fingers inside every logged-in app* — read any active window's text, screenshot it (API 30+), tap/type as the user. Session exposure is total: messages, email, banking-adjacent flows that aren't `FLAG_SECURE`, OTPs displayed in notifications/apps. AGI's own pitch — “every app you're logged into, no integrations” — is simultaneously its threat model.
- **Phone-as-toolbox pattern:** narrower but still sensitive in bulk: contacts + SMS + files + camera + precise location + sensor history (Premex, PhonePi, htekdev). Premex mitigates best-in-class here: every tool off until enabled, sensitive tools need explicit consent, bearer locally / OAuth 2.1 remotely, revocable paired-client list, Keystore-backed token storage (Play + repo, verified live).

**Credential/session exposure & logging:**
- Screenshots and UI trees are *sent to the model provider* in every vision/tree-based system — “local-first” describes the transport, not the inference. ScreenSync's comparison page states this honestly for all servers including its own; Mika's README states “what you say and what's on your screen go only to the model provider you set up.” Budget accordingly: a UI tree is cheaper *and* less leaky than screenshots; both can contain OTPs, addresses, and message content.
- Brokers/relays see whatever passes through them. viandwi24: one shared `PHONE_MCP_TOKEN` guards *both* the phone and the agent side, tokens travel in the WebSocket URL/header — the README itself warns to put the broker behind HTTPS/`wss://` or the token goes in clear text; there is no per-device or per-client credential separation and no revocation short of rotating the one token. AGI/Melaya/Mobilerun clouds necessarily see task prompts and progress/result streams (their docs describe cloud dispatch/monitoring); Melaya claims frames are streamed only while watched and never stored, and device tokens are stored server-side *as hashes* (vendor claims, verified as published).
- **Notable safeguards worth copying:** Melaya's double-enforced per-app allowlist (server checks before queueing; the app re-checks the foreground package before executing) + HITL gates for publish/send/spend/delete/account changes + short-lived single-use pairing codes; AGI/Mika's hand-back of logins/payments/CAPTCHAs (Mika additionally: computer-submitted tasks *cannot* approve gated actions — approval must happen on the phone; its LAN mode is off by default, plain HTTP, LAN/private-VPN addresses only); DroidMind's shell allowlist + risk tiers + audit logging; Premex's off-by-default tools.
- **Red flags found in the wild:** (1) htekdev/phone-mcp-server — **no authentication by default** on a server that can send SMS and place calls, discoverable by anyone on the LAN. (2) Any server exposing a **raw shell/ADB tool** to a general-purpose LLM client (prompt injection in a web page/message the agent reads becomes command execution — one MCP-workshop post in the index recounts an agent leaking an emailed OTP after a planted “ignore previous instructions” page). (3) phone-mcp.com/PhoneMCP — commercial SMS product with no visible pricing, maker, privacy policy or repo on its homepage. (4) Debug-signed release APKs (viandwi24's default) and sideload-only distribution generally: no store review, update integrity rests on the repo. (5) “Anti-detection” sections (viandwi24's architecture doc discusses human-like pacing to evade automation detection, and its stated use case is TikTok profile checking at volume) — a ToS/abuse signal, and a warning that such use cases drive platform countermeasures.
- **Prompt-injection is the category's core unsolved problem:** the agent reads untrusted screen content (messages, web pages, app UIs) with the user's full session privileges. No surveyed product offers a technical defence beyond allowlists, HITL gates, and read-before-act verification.

### 6. Prior art and adjacent approaches a builder should know

- **Open-AutoGLM (zai-org)** — the reference open phone-agent *framework* (not MCP-native): AutoGLM-Phone-9B vision-language model + screenshot→plan→act loop over ADB (Android 7+), HDC (HarmonyOS), WDA (iOS, experimental); needs ADB Keyboard for reliable text input; Wi-Fi remote ADB supported; **repo terms restrict it to research/learning**. Differentiation: it ships the *brain* (a phone-tuned VLM); MCP servers ship only the *hands*. https://github.com/zai-org/Open-AutoGLM/blob/main/README_en.md (index).
- **AndroidWorld (Google DeepMind, ICLR 2025)** — benchmark every builder should calibrate against: 116 tasks across 20 real apps on an emulator, with programmatic success checks; the paper's best agent completed **30.6%** of tasks vs 80% human (arXiv:2405.14573, https://arxiv.org/html/2405.14573v3, index). Any vendor claiming near-human phone autonomy is claiming to beat a benchmark where the reference agent failed 7 times in 10.
- **DroidRun → Mobilerun** — the closest commercialised relative of the user's design before Mika: open framework + Portal accessibility app locally, then a cloud layer (your phone or rented phones) with API/MCP, credits and fleet management. Lesson: the monetisable layer turned out to be *hosting, identity and fleet*, not the control primitives (those commoditised to MIT/Apache within a year).
- **Appium / XCUITest / Espresso / Maestro lineage** — the testing world's decade-old stack that most MCP servers wrap (mobile-mcp began as WDA+ADB glue; Maestro now ships its own MCP server). Their locator/idempotency/wait-condition discipline is the part LLM-first projects keep re-learning.
- **agent-device (Callstack), MobileBuildMCP/XcodeBuildMCP, Drengr, MobAI, Limrun** — developer/QA-flavoured MCP device drivers, incl. device-farm backends (BrowserStack/Sauce/AWS Device Farm/LambdaTest) behind one MCP surface (index comparison: https://dev.to/alon_n_ecceca6aa868e0761d/the-best-android-mcp-servers-in-2026-twelve-compared-local-and-hosted-3om). Relevant if the user's system ever needs CI/simulator/farm targets, not for a personal signed-in phone.
- **Computer-use phone agents from the labs** — Google's Gemini Computer Use (claims leading AndroidWorld results, vendor claim), Anthropic/OpenAI computer-use via mirroring (e.g. Yutori's plan benchmarks iPhone Mirroring as a control surface: pixel screenshot + Mac input forwarding while the phone stays locked — https://github.com/yutori-ai/yutori-mcp/blob/HEAD/plans/001-mobile-computer-use.md, index). Differentiation for an independent builder: labs supply models; the durable independent layer is the *device bridge + policy + orchestration*.
- **SMS-gateway MCPs (textbee, Sparetext)** — adjacent proof that narrow, OS-sanctioned capabilities (default-SMS role on Android; Text Message Forwarding + Mac relay on iOS) can be productised without any UI automation at all.

### 7. Builder-focused comparison: patterns worth copying vs traps

*For: an on-device Android agent/bridge on a BLU View 5-class phone (Android 14, 3 GB RAM), remotely orchestrated, where ordinary paired-device channels lack shell/ADB/tap automation.*

#### Copy these
1. **viandwi24's topology, hardened.** On-device foreground service holding **one persistent outbound WebSocket** to a broker (works behind NAT, no listening port on the phone, no cable, no host PC); MCP server as a thin stdio/HTTP shim *next to the orchestrator*, not on the phone. Stateless-ish broker, in-memory device registry, `reqId`-correlated commands with timeouts. This is the only surveyed topology that survives the phone leaving the desk — which ADB patterns (hao-cyber, mobile-mcp, Android-MCP) fundamentally cannot.
2. **Compact snapshot-with-refs as the primary observation** (viandwi24: one line per meaningful node, `[n12]` refs, 300-line/~12 KB cap, stale-ref errors, one-line action results with a “now: <app> — <title> (screen changed)” hint; mobile-mcp and Melaya converge on the same idea). On a 3 GB phone and a paid-by-token model this beats screenshot-per-step on cost, latency *and* leakage. Screenshots only for canvas/video/custom-drawn surfaces.
3. **Intent/deep-link first, gestures last** (viandwi24's stated principle): `open_url`/explicit intents for navigation; node actions (`ACTION_CLICK`/`ACTION_SET_TEXT`) before coordinate taps; coordinate taps only with a fresh snapshot. Blind tap chains are Melaya's named anti-pattern (“observe, act, verify, then continue”).
4. **Melaya-grade policy enforcement on-device.** Allowlist checked in the broker *and again on the phone against the actual foreground package/display* before execution; HITL gates for send/publish/spend/delete/account changes that **cannot be satisfied by the remote caller** (Mika's rule: computer tasks can never approve gated actions — approval happens on the phone); visible overlay + hardware-obvious stop control during foreground runs; pairing codes short-lived and single-use; device tokens stored hashed server-side and individually revocable (Melaya/Premex patterns).
5. **Mika's virtual-display path — if true concurrency is a requirement, and only then.** Shell-identity helper started via one-time wireless-debugging pairing (+ USB fallback script; expect to re-start after reboot, as with Shizuku) → VirtualDisplay → launch/inspect/act there. On Android 14 the background display's independent focus makes this genuinely usable. Keep a foreground-display mode as the default/fallback: more apps work there.
6. **DroidMind-style guardrails around any shell escape hatch.** If the bridge exposes shell (the gap the user specifically noted in paired-device channels), expose *named, parameterised operations* first; if a general shell tool must exist, gate it with an allowlist, risk tiers, blocked-by-default critical commands, and a full audit log — never ship htekdev-style unauthenticated LAN access.
7. **Honest lock/FLAG_SECURE semantics** (viandwi24): wake-on-demand, dismiss only swipe/none locks, auto-relock only if you woke it, hard-fail with “unlock it on the device” on credential locks, black-frame detection for `FLAG_SECURE`. Never attempt PIN entry over injected input as a “feature” — it converts a tool into a credential-theft surface.
8. **Survival engineering for cheap OEM phones:** foreground service with correct typed FGS declarations (mediaProjection type if used), battery-optimisation exemption requested in onboarding, auto-reconnect with exponential backoff + heartbeat, boot-recovery story stated honestly (unrooted shell helpers and MediaProjection consent do not survive reboot — design re-pairing to be one tap, not a re-install), Accessibility `takeScreenshot()` (API 30+, no consent dialog, no per-session expiry) preferred over MediaProjection for stills.

#### Traps
1. **Believing “background” marketing — including your own.** Accessibility and ADB both drive the *foreground* display. Shipping foreground automation labelled “background” produces the classic failure: agent and user interleaving input, focus theft mid-typing (a documented Android 12–13 virtual-display issue too), and tasks corrupted by an incoming call UI. Decide explicitly which of senses A/B/C each feature is, and say so in the UI.
2. **Google Play distribution for an autonomous Accessibility agent.** Play policy states the Accessibility API is not designed and cannot be requested for “an app that autonomously initiates, plans, and executes actions or decisions”; non-accessibility-tool uses need a Play Console declaration, prominent disclosure and affirmative consent (https://support.google.com/googleplay/android-developer/answer/16558241, index). Every serious project here sideloads, self-distributes, or (Premex) avoids UI automation on Play entirely. Plan distribution (sideload/enterprise/direct APK) as a product decision, not an afterthought — and remember sideloading triggers Android 13+ Restricted Settings friction in onboarding.
3. **Single shared token / cleartext transport.** One token for phone+b broker+agent (viandwi24) means one leak = full phone compromise, with no selective revocation. Use per-device credentials, TLS (`wss://`) by default, short-lived pairing, and revocation lists from day one — retrofitting identity into a broker protocol is painful.
4. **Raw shell + an LLM that reads screens = prompt-injection RCE on a signed-in phone.** Any page/message/app the agent *reads* can instruct it. Mitigations are partial only: allowlists, HITL on irreversible actions, separating “read” tools from “act” tools, and never letting screen content mint new permissions.
5. **MediaProjection as your screenshot foundation.** Per-session consent (Android 14 token single-use; Android 15 re-grant), auto-stop on lock (15 QPR1), status-bar chip, and OEM variance make it a poor always-on channel. It's a fallback, not a backbone.
6. **Screenshot-first perception on low-end hardware.** Full PNGs from a Helio A22/3 GB device over a phone uplink, per step, to a vision model: slow, expensive, and the leakiest option. Tree-first, screenshot-on-doubt (mobile-mcp's positioning) is the correct default; OCR (Mika bundles it) belongs on-device only if the budget allows — on this class of hardware, prefer server-side OCR of an occasional cropped screenshot.
7. **Assuming the helper survives.** Wireless debugging turns itself off on Wi-Fi change/reboot (Mika's FAQ admits it must turn it back on “with your permission”); OEM task killers (Xiaomi/Oppo/Vivo/Samsung named by viandwi24; BLU's near-stock build is kinder but 3 GB RAM is not) will kill your service. Heartbeat + watchdog + degraded-mode reporting to the orchestrator (“device present but helper down — needs one tap”) beats silent failure.
8. **One phone = one session.** viandwi24 and ScreenMCP both state it; virtual displays don't create parallel *users* — notifications, audio, telephony, and many apps are singletons. Fleet scale = more physical phones (Mobilerun's whole business), not more sessions per phone.
9. **Benchmark/marketing reliability claims.** AndroidWorld's 30.6% reference result (§6) vs vendors' “operates any app” copy: design the orchestration for *supervised, resumable, step-verified* tasks with hand-back, not fire-and-forget autonomy — especially for messaging/payment-adjacent flows in logged-in apps.
10. **iOS as a roadmap checkbox.** There is no on-device background-control path on iOS, period (§3.3). An iOS story means a Mac-attached WDA runner, iPhone Mirroring, a cloud device, or a narrow sanctioned capability (SMS via Mac relay, Shortcuts/App Intents) — budget it as a separate product surface or drop it.

#### Architecture verdict for this builder
The user's instinct (on-device agent + remote orchestration) matches the strongest pattern in the field (viandwi24 topology; Mika's execution model; Melaya's policy model). The differentiated, defensible stack is: **thin Kotlin agent (ForegroundService + Accessibility; shell helper via wireless-debugging pairing only if virtual-display concurrency or shell-level ops are truly needed) → outbound WSS to a broker with per-device identity → snapshot-first MCP tools with on-device policy enforcement and phone-only approval for gated actions → orchestrator-side planning with screenshot fallback.** The parts *not* worth building: another ADB host server (commoditised), a proprietary cloud relay before the local/self-host path is solid, and any iOS UI-control promise.
