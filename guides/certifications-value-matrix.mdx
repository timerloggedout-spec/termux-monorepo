## Rules of This Matrix (DoE conformity — binding)

- Every cell is an **expectation record**, not a bare number: it carries a value or range **and** its basis — `measured` (telemetry/capture of record), `issuer` (platform-published rule), `assumption` (labelled, re-priced at first instance), or **INTAKE/HELD** (unevidenced — no value claimed).
- The ALE view and this matrix are **derived views of the same numbers**. No cell is computed twice from different inputs.
- **Unevidenced cells carry INTAKE/HELD. There are no dressed-up zeros in this document.** A `0` appears only where zero is itself the evidenced value (e.g. completions counted on the record).
- Earner = `termux-monorepo` ∀ rows. The certifications tree manages (oversight, enrolment, evidence); it does not earn. Completion ⇔ fleet-automation run ∧ telemetry-evidenced ∧ per-model attribution on record (`docs/ops/CERTIFICATIONS-PROGRAM.md`, PR #3249).
- Dates columns (wall + buffer-landing) and evidence-state column are supplied by the Roadmap lane and reconciled into this single matrix; ladder is rows-of-record owner.
- Buffer rule (owner, 2026-11-02): dated items land −1d ahead of wall; landing dates govern.
- **Two axes, mechanical (DoE F2):** every record carries `basis_kind` ∈ {measured · issuer · assumption} AND `state` ∈ {CORROBORATED · PROVISIONAL · INTAKE · HELD · NOT_ESTABLISHED}. An assumption-basis cell is **prior-only**: its posterior carries the value flagged PROVISIONAL/INTAKE — never silently priced.
- **Record shape (DoE F1):** per cell {quantity · prior{value · range · basis_kind} · evidence[{source · direction · strength · rule9_state}] · posterior{value · range · updated_at · n_evidence} · state} — the posterior is recomputable from the legs. Records home: `guides/certifications-value-matrix.records.json` (one home, beside this render).
- **Tier labels are DERIVED (DoE conformity PASS, 2026-11-02):** every assignment carries derivation citations {tier · records cited · function version} (DoE F6/F8); a tier change is a re-derivation event against the records, never an edit.

## Population — the "=+" Equation (owner, 2026-11-02)

The population of this matrix is an **equation, not a list**:

**Population = baseline ladder + named additions (deduped) + active/competition rows + open INTAKE "++" additions.**

The owner-named security families are **baseline rows of record** — not new candidates, not a side-list: **L2 CTF / OverTheWire** (#342 surfaces) · **L3 CompTIA suite** · **L5 Offensive Security / OSCP** · **L6 CISSP (ISC2)**. Each is its baseline row in the matrix above, carrying its evidence gap in-row (state = INTAKE + gap named until a Role Requirements Plan prices it). Owner naming = **inclusion prior only** (DoE conformity note, PR #3786): a named row joins with INTAKE cells + an evidence_requirement — **naming moves no posterior, prices no cell**; every value cell stays evidence-gated.

**Dedupe rule (DoE, PR #3786):** the equation dedupes against the ladder of record — a baseline row enters the matrix **once**, carrying its existing state; the matrix never forks a second copy of a ladder row. INTAKE rows for the same providers are **pricing-grain children, not copies**: provider wider-family rows cover only certs *beyond* the baseline picks, and per-platform rows (L2 / L4) carry platform censuses while the parent rung row carries sequence + state — no cell is stated twice. A "++" addition that duplicates a ladder row is a **dedup defect**, flagged and removed. "++": the census stays **OPEN** — new families keep being added as discovered, INTAKE-first, never a closed list.

## Linked Layers — Dependency Edges + Value-Cap (extension of the delineation of record)

The skills/learnings ↔ certifications mapping is **already delineated** by the derived-artifacts program rule of record (`docs/ops/CERTIFICATIONS-PROGRAM.md`, PR #3249; planes delineated 2026-10-30): per-rung derived {skills · KB} in the completion package · evidence spec {skill refs · KB refs} · capture-as-you-go · monorepo-first placement · **Evidence ≠ SKILL.md** · Flows / Learnings / Knowledge as separate planes. **This matrix conforms to that delineation — ∅ parallel layering, ∅ restatement.** Per-rung derived refs stand at ∅ / ¬built ∀ rungs, exactly as the ladder ledger carries them; the Learnings planes (`archwiz/LEARNINGS.md` TIL · `docs/ops/sessions/LEARNINGS-ADDENDUM.md` symptom→root-cause→fix · `docs/icm/objects/knowledge/*`) are cited, not re-tabled.

Only two elements here are genuinely new, folded in **only where they extend** the delineation — under the DoE dependency-graph frame (PR #3787, correction PR #3788: the genuinely-new set is exactly the dependency cap, the leverage derivation, and the edge citation discipline). **Governing rule:** where the cap/leverage/edge elements conflict with the delineation of record, **the delineation governs** — the conflict returns to DoE as a finding, never a silent override. Conformity of all skills/learnings content is read against the delineation, not against the graph frame.

1. **Dependency edges** — every skill/execution chain carries its dependency set {tools · workflows · connectors · provider arms · data feeds}, and every tool carries **reverse edges** (tool → skills/rows it enables), tabled below. **Type discipline:** a Learning is an evidence input, never a skill; a Skill is a capability definition, never evidence — a learning record feeds posteriors, it never becomes a capability claim. **Edges are records** {n · stratum · basis} under the same citation discipline; ∅ edge from naming alone — a plausible chain without an evidence basis is an **INTAKE edge**, labeled as such.
2. **Value-cap treatment** — a cert's value includes the skills it develops; a skill's value record cites its dependency state as an evidence leg. **Dependency cap:** a *critical* dependency down/blocked ⇒ the claim is **CAPPED at HELD** until redundancy/failover is **TESTED** (asserted redundancy doesn't lift the cap; a test record does). **Criticality test (three states, DoE G1):** a dependency is **CRITICAL** iff it is the sole evidenced path for its stratum (n = 1) ∨ its failover is asserted-but-untested; **NON-critical** iff ≥2 independent evidenced paths exist ∧ a failover TEST record exists; **criticality INTAKE** = the middle state (n ≥ 2 ∧ failover neither asserted nor tested) — its consequence: the dependency leg counts **single-leg/provisional** in the dependent record (¬ a HELD cap, ¬ a pass). Criticality re-derives from the edge records, never edited. **Tool leverage = Σ-derived** from downstream skills' records — ∅ tool-local score field anywhere in this graph.

The layer list stays **OPEN** ("etc"), same as the census. Conformity clauses (1)–(6) apply to these cells too. Graph records live in the same record home as the matrix records (`guides/certifications-value-matrix.records.json`, `graph` section: nodes + edge records).

## INTAKE — Certifications as a Category (not yet enrolled)

The matrix covers **Certifications as a category**, not only the enrolled ladder. Every cert family/provider of record across the L1–L6 categories appears below as an **INTAKE row** until it is enrolled. INTAKE rows carry **no estimated values** — each names **the gap**: the specific evidence that would price the row and promote it to a full expectation record above.

The INTAKE row set is an **accumulation queue** (DoE amendment, PR #3784): every row names its `evidence_requirement`; a row lacking one is a queue defect. Two reads are served: (1) sequencing the active track (matrix above), and (2) prioritizing what enters it. An INTAKE row is promoted when its gap evidence lands and a Role Requirements Plan (plan-before-spend) is opened for it; promotion order = competition linkage first, then deadline, then target-role gap fit, then cost class.

**Requirement vocabulary — ADOPTED as the vocabulary of record (DoE verdict 2026-11-02, 6 classes; seed classes from DoE, † = drafted here and accepted with the boundaries stated).** Requirements are tagged per row so accumulation work is comparable across rows:

- `issuer-page` — issuer-page verification: the issuer's own catalogue/page {credential name, exam structure, fee, validity} → prices payoff class + cost/time priors.
- `cost-feasibility` — cost/feasibility read: total cost, card-gate class (fleet rule: card-gated ⇒ CLOSED class), fleet-route (workflow) feasibility → prices cost/quota cells.
- `competition-link` — competition-requirement link: a competition rules/milestones page naming the cert or gate → prices competition payoff + tier-derivation inputs.
- `completion-precedent` — completion-evidence precedent: a completion on record {cert ref · points ref · fleet run / model / telemetry} → moves INTAKE cells to posterior.
- `census` † — platform/family census: structured enumeration {tracks, credential issued if any, tiers} — the raw read the other classes draw from for multi-cert families and platforms. **Boundary (DoE, adopted):** a census discharges an *enumeration* requirement only — it prices nothing by itself; a completed census leaves cells INTAKE until a pricing class lands on the enumerated items.
- `plan` † — Role Requirements Plan (pre-spend plan of record) → prices the gated ladder rows (L3 / L5 / L6 pattern). **Boundary (DoE, adopted):** plan-derived values enter at `basis_kind = assumption` (prior-class), never measured/issuer, until execution or issuer verification re-bases them; for the gated rows the pre-spend plan IS the operative record — prior-grade evidence.
