# RFP: RHYTHMIC SYSTEMS — A Temporal Intelligence & Orchestration Architecture

<badge color="success">RECOMMENDED FOR ARCHITECTURE EXPLORATION</badge> <badge color="info">PRE-DISPATCH REVIEW</badge>

**My strongest recommendation: don't build a conventional `Rhythms` section. Build a new conceptual layer around TIME, PHASE, RELATIONSHIP, SYNCHRONIZATION and COMPOSITION.**

Rhythm is the entry point. The real opportunity is much bigger.

You're describing something that could become an entirely new dimension of the Termux MonoRepo: a system that understands how independent processes, agents, workflows, events, measurements and creative compositions coexist in time.

Think of it as an orchestra whose musicians are agents, whose score is executable, whose conductor is an orchestration manager, and whose performance is continuously measured.

But let's take that further.

# 3. The mathematical opportunity: overlapping subdivisions

This is where your fractional notation becomes particularly interesting.

You're describing something beyond conventional musical meter.

Consider:

\[
\frac12,\frac13,\frac14,\frac15,\frac38,
\frac25,\frac23,\frac34,\frac45,\frac56
\]

These can represent different subdivisions or phase relationships over a shared temporal interval.

For example, take a common interval of 60 seconds.

Now translate that into software.

| Temporal layer | Possible application |
|---|---|
| 1/2 | Half-cycle execution |
| 1/3 | Three-stage evaluation |
| 1/4 | Four-phase orchestration |
| 1/5 | Five-part observation cycle |
| 3/8 | Cross-cycle subdivision |
| 2/5 | Relative scheduling ratio |
| 4/5 | Completion threshold or phase position |

The critical mathematical distinction:

**A fraction must have an explicit semantic type.**

`3/8` could mean:

- A subdivision of a bar.
- A relative phase.
- A proportion of a duration.
- A scheduling ratio.
- A probability.
- A resource allocation.

These are not interchangeable.

I would establish a typed temporal notation registry rather than overload ordinary fractions.

### The interesting mathematical machinery

I'd investigate:

1. Rational arithmetic instead of floating-point timing.
2. Least common multiples for shared subdivision grids.
3. Greatest common divisors for rhythmic normalization.
4. Modular arithmetic for recurring event alignment.
5. Phase offsets for independent cycles.
6. Polymetric relationships.
7. Euclidean rhythm generation.
8. Tempo maps and variable-rate execution.
9. Drift and synchronization error.
10. Event collision detection.

For example:

\[
LCM(2,3,4,5,8)=120
\]

That gives a common subdivision lattice for those five independent patterns.

This could become a powerful scheduling and simulation primitive.

However, don't confuse musical alignment with operational correctness. Actual workflows must still use explicit event dependencies, clocks, deadlines and execution guarantees.

## 5. Mathematical and temporal engine

### 5.1 Exact arithmetic

Use reduced rational values (numerator/denominator), positive denominators, deterministic normalization, and integer/rational operations. Reject binary floating-point timing inputs at the core boundary. Decimal input, if needed at a UI boundary, must be converted from its canonical decimal string and retain the conversion provenance.

The common subdivision lattice is based on the least common multiple of denominators. For example, subdivisions `1/2`, `1/3`, `1/4`, `1/5`, and `1/8` yield 120 ticks per base unit. This is a mathematical illustration; production resolution must be bounded by explicit event-count and resource limits.

For positive rational cycle periods `p_i/q_i` in reduced form, calculate the least common repeat interval as `lcm(p_i) / gcd(q_i)`. Use exact modular arithmetic for phase alignment and collision detection.

### 5.2 Time domains must remain separate

Use distinct types/adapters for:

1. abstract beat/cycle time;
2. UTC wall-clock time for repository records and scheduled workflows;
3. monotonic runtime time for elapsed-duration measurement;
4. audio sample/frame time for Music-as-Code tools;
5. Temporal.io workflow time for durable execution.

Never silently compare or convert these clocks. Conversions require an explicit tempo map, sample rate, timestamp source, or workflow-time adapter.

### 5.3 Core functions

- parse and normalize typed ratios;
- compute denominator lattice and common cycle;
- generate deterministic event sequences under a declared horizon;
- normalize phase offsets modulo the declared cycle;
- detect exact simultaneous events and phase collisions;
- identify drift only when observed timestamps and clock uncertainty are available;
- cap event counts, cycle horizon, denominator growth, and simulation memory;
- return stable event ordering and reproducible result hashes.

The engine is a deterministic simulator/analysis library. It is not a background scheduler, timer service, or replacement for the dependency-phase engine.

1. abstract beat/cycle time;
2. UTC wall-clock time for repository records and scheduled workflows;
3. monotonic runtime time for elapsed-duration measurement;
4. audio sample/frame time for Music-as-Code tools;
5. Temporal.io workflow time for durable execution.

Never silently compare or convert these clocks. Conversions require an explicit tempo map, sample rate, timestamp source, or workflow-time adapter.

### 5.3 Core functions

- parse and normalize typed ratios;
- compute denominator lattice and common cycle;
- generate deterministic event sequences under a declared horizon;
- normalize phase offsets modulo the declared cycle;
- detect exact simultaneous events and phase collisions;
- identify drift only when observed timestamps and clock uncertainty are available;
- cap event counts, cycle horizon, denominator growth, and simulation memory;
- return stable event ordering and reproducible result hashes.

The engine is a deterministic simulator/analysis library. It is not a background scheduler, timer service, or replacement for the dependency-phase engine.

## 6. Orchestra Conductor implementation

### 6.1 Role and inputs

Orchestra Conductor is a Tier-2 orchestration treatment under the existing Manager. It consumes:

- a canonical task/dependency plan;
- phase-engine readiness and wave information;
- an optional Ballet choreography plan;
- section/task ownership and write-set metadata;
- typed cycle periods, subdivisions, and phase offsets;
- the manager-selected policy and wait/retry contract.

It does not create dependency edges, select providers, claim work, own execution adapters, or certify task success.

### 6.2 Score and section model

A score is a typed description of work sections. Each section maps a set of task IDs to an execution role and carries optional cycle/phase/subdivision metadata. A task belongs to exactly one section in a given score. The plan must account for every task exactly once; unknown, missing, or duplicated task IDs fail validation.

The conductor emits a deterministic cue sheet. Initial cue vocabulary:

- `PREPARE` — make the section ready for an admitted wave;
- `ENTER` — issue a manager-approved entry intent;
- `WAIT` — hold while authoritative readiness/evidence is incomplete;
- `REHEARSE` — run a bounded, non-mutating dry run or fixture validation;
- `SYNC` — compare phase/evidence state at a declared checkpoint;
- `HANDOFF` — record the transition between sections or specialists;
- `INTEGRATE` — collect the section outputs for integration;
- `VERIFY` — run the declared validation contract;
- `STOP` / `CANCEL` — record explicit terminal or cancellation cues.

Every cue has a stable ID, rational time, source plan/SHA, section/task IDs, dependencies, and evidence references where available.

All three placements use the same cue semantics, task cohorts, validation, and evidence contract. Placement is an experiment factor, not a production authority grant.

### 6.4 Strategy treatments

Compare the incumbent manager policy and Ballet Coordinator against:

- `sequential`: one task entry at a time inside an admitted wave;
- `parallel`: independent tasks in the same admitted wave enter together;
- `adaptive`: cue/wait decisions react to authoritative progress and evidence, never to elapsed time alone.

Adaptive waiting follows the existing repository rule: progressing or useful work continues; repeated identical state triggers investigation; verified failure is classified before retry; no arbitrary short timeout overrides useful work.

## 9. What I would investigate beyond the obvious

1. **Clock ontology:** how abstract beat time, UTC, monotonic time, audio samples, and durable-workflow time map without accidental comparison.
2. **Causal order versus phase alignment:** dependency edges establish causality; rhythmic phase only expresses timing relationships. A phase collision must never override a dependency.
3. **LCM explosion:** large or coprime denominators can create huge lattices. Establish maximum denominator, horizon, event count, and memory budgets before expanding the notation vocabulary.
4. **Typed fraction semantics:** distinguish subdivision, cycle period, phase offset, duration, tempo ratio, probability, and resource share; preserve semantic kind through serialization and compression.
5. **Clock drift and uncertainty:** distinguish observed scheduler jitter from source-clock skew, measurement error, and deliberate phase offsets. Avoid declaring synchronization failure without clock uncertainty bounds.
6. **Phase locking and feedback stability:** test whether adaptive cue policies oscillate, over-correct, or starve slow sections. Include hysteresis and minimum evidence requirements where justified.
7. **Fairness and starvation:** measure whether fast/short sections monopolize capacity while long-running sections are repeatedly deferred.
8. **Failure semantics:** define cancellation, unknown outcomes, duplicate claims, idempotency, partial completion, compensation, and retry boundaries before any live dispatch adapter is enabled.
9. **Polyphony versus write conflicts:** parallel musical parts do not imply safe parallel writes. Model task write sets and serialize conflicting writers regardless of rhythmic alignment.
10. **DoE validity:** control for task difficulty, provider/model configuration, quota resets, cohort drift, selection bias, multiple comparisons, winner's curse, and missing/censored observations.
11. **Human interpretability:** test whether a cue sheet improves operator understanding or simply adds notation. Provide plain-language projections and accessible text-only views.
12. **Music tool provenance and security:** record tool versions and source hashes; keep untrusted score/code execution isolated and optional.
13. **Termux resource envelope:** measure CPU, memory, thermal throttling, storage, and battery before choosing a local simulation horizon or visualization strategy.
14. **Notation evolution:** preserve canonical/domain-specific distinctions, aliases, provenance, deprecations, and registry evolution history. Generated views remain projections, never source of truth.
15. **Temporal.io coexistence:** define a clear adapter boundary so durable workflow execution can consume or emit timing metadata without importing the Rhythmic Systems domain as a second workflow runtime.

## How this maps into the existing Termux monorepo

The repository already has most of the runtime substrate. The missing piece is a **shared temporal contract** connecting planning, assignment, waiting, collection, and evidence.

| Existing subsystem | Temporal extension | Ownership boundary |
|---|---|---|
| Dependency-phase engine | `READY_AT`, `NOT_BEFORE`, dependency barriers | Owns canonical readiness and claims |
| Ballet Coordinator | `WAVE`, `PHASE`, `WINDOW`, `EXPECTED_DURATION`, `CONCURRENCY` | Plans safe waves; does not dispatch |
| QUE / priority windows | `OPEN`, `CLOSE`, `DEFER`, `EXPIRE`, `QUEUE_WAIT` | Owns admission, queue and claims |
| `WAIT → WATCH` loop | `WAIT_UNTIL`, `WAKE_ON`, `RECHECK_AT` | Keeps independent work moving while a cohort waits |
| Existing QUE collector | `QUEUED`, `STARTED`, `COMPLETED`, `CANCELLED`, `VANISHED` | Emits observed lifecycle facts |
| ATES / canonical receipts | `EXPECTED`, `ACTUAL`, `DRIFT`, `EVIDENCE_COMPLETE` | Records outcomes; never infers success from a plan |
| DoE / Observatory / Moneyball | timing-policy factors and measured effects | Compares treatments; does not promote them |

This is grounded in existing repo contracts: QUE already records run transitions and queue-wait seconds; its collector distinguishes a run that vanished from the census from one with a completed record. Its priority-window feed already has `active`, `closed`, and `unknown` states. The integration plan explicitly says `WAIT` is active-work state: independent non-conflicting work continues while the watched cohort is rechecked at the next evidence boundary.

Sources: [`ops/que/README.md`](https://github.com/timerloggedout-spec/termux-monorepo/blob/master/ops/que/README.md) · [`scripts/que/que_feed_collect.py`](https://github.com/timerloggedout-spec/termux-monorepo/blob/master/scripts/que/que_feed_collect.py) · [`docs/ops/AGENTIC-INTEGRATION-PLAN-STATUS.md`](https://github.com/timerloggedout-spec/termux-monorepo/blob/master/docs/ops/AGENTIC-INTEGRATION-PLAN-STATUS.md)

**Critical gap:** the Ballet reference implementation currently models dependency waves, write-set conflicts, `parallel_safe`, and estimated task duration. It does not yet model assignment open/close windows, asynchronous completion futures, wait predicates, collector cadence, expected completion intervals, or observed temporal drift. Its own RFP says it consumes dependency readiness and leaves execution/evidence to existing systems. So the right move is to extend Ballet’s *plan representation and DoE factors*, not make Ballet a scheduler.
