# Google Stitch Skills — refTemplates entry (pattern from Google Labs' Agent Skills library for the Stitch MCP server)

- **What:** A library of Agent Skills that plug coding agents into Google Stitch (Google Labs' AI UI design tool) through its MCP server — agents generate screens from text or images, edit screens in place, manage design systems, and convert designs back to code. The skills carry instructions only; every capability lives behind the Stitch MCP server.
- **Source:** Repository (README, plugin manifests, skill definitions read firsthand) — https://github.com/google-labs-code/stitch-skills · Stitch — https://stitch.withgoogle.com (MCP setup + docs at stitch.withgoogle.com/docs) · Agent Skills open standard — https://agentskills.io

## The pattern (what we copy)

- **One open standard for the skill package.** Every skill follows the Agent Skills standard (agentskills.io): a folder whose `SKILL.md` is the "mission control" — YAML frontmatter (`name`, `description`, `allowed-tools`) plus a procedural body — accompanied by `scripts/` (executable enforcers: validation & networking), `resources/`/`references/` (the knowledge base: checklists, style guides, keyword maps), and `examples/` (gold-standard syntactically valid references). The package is host-neutral Markdown + files; no runtime code of Google's ships in the skill itself.
- **A plugin layer above the skills.** Skills are bundled into three plugins, each just a `plugin.json` manifest (name, description, version, author, license, keywords) over a `skills/` tree: `stitch-design` (6 design-workflow skills), `stitch-build` (5 code-generation skills), `stitch-utilities` (5 prompt/spec/standards skills). Distribution rides each host's own marketplace mechanics: a marketplace manifest at `.agents/plugins/marketplace.json` for Codex (`codex plugin marketplace add … --sparse …`), `npx plugins add google-labs-code/stitch-skills --target claude-code|cursor` for Claude Code and Cursor, `npx skills add …` for selective per-skill installs.
- **Skills = a thin instruction layer over one MCP server.** All state and generation live in the hosted Stitch MCP server (remote endpoint + credentials provisioned through the Stitch MCP setup flow, per-agent config). The skills only choreograph its tools — `list_projects`, `create_project`, `list_screens`, `get_screen`, `generate_screen_from_text`, `edit_screens`, `generate_variants`, `list_design_systems`, upload tools — and the choreography is capability-scoped in frontmatter (`allowed-tools: "stitch*:*", Bash, Read, Write, web_fetch` on `stitch::generate-design`). Host differences in MCP tool prefixes are explicitly delegated to the host's system prompt, not patched per skill.
- **A prompt-enhancement pipeline inside the skill.** Before any generation call, `stitch::generate-design` runs a fixed pipeline: analyze context (find/create the project; check `list_design_systems` — if a design system exists, tokens are already applied at project level), refine terminology against bundled reference maps (vague → professional UI/UX vocabulary), structure the prompt on a template (purpose, PLATFORM, PAGE STRUCTURE), then surface the tool's `outputComponents` (text description + suggestions) after every call. Four flows branch off one mode decision: Generate from Text · Generate from Image (delegate upload, then edit-refine) · Edit (targeted prompt, iterate, never re-generate unless layout is wrong) · Generate Variants (`variantCount` 1–5, `creativeRange` REFINE/EXPLORE/REIMAGINE, `aspects` LAYOUT/COLOR_SCHEME/IMAGES/TEXT_FONT/TEXT_CONTENT).
- **Theme is owned by the design system, never by the prompt.** Generation prompts are forbidden from carrying hex codes, font names, palettes, or roundness — tokens live in the project's design system and would conflict if duplicated (edit prompts may use hex for precise fixes). Content/structure and theme are separate channels with separate owners — the skill's central discipline.
- **DESIGN.md as the portable design-system artifact.** A small skill family treats one Markdown file as the token contract: `stitch::extract-design-md` derives it from frontend source, `stitch::manage-design-system` uploads it and applies themes to screens, `design-md` generates it from a Stitch project analysis, `taste-design` generates it under premium/anti-generic constraints. A sibling artifact, SITE.md (`site-md`), acts as a project "constitution" for the Stitch Build Loop. Downloaded screens land in `.stitch/designs/` with a `.stitch/metadata.json` tracking screens/device types/design system — local files mirror server state.
- **A bidirectional code↔design loop.** `stitch::code-to-design` lifts existing frontend code into a Stitch design (HTML extraction + design system + upload); `stitch::extract-static-html` snapshots running apps into self-contained HTML; the build plugin runs the return path — `stitch::react-components` and `stitch::react-native` convert screens to component systems with automated validation and token consistency, `react-vite-dashboard` targets React+Vite+TanStack, `shadcn-ui` is pure guidance, `remotion` renders walkthrough videos from projects; `stitch-loop` closes the loop end-to-end (one prompt → complete multi-page site with automated validation).
- **Skills compose by naming each other.** `generate-design` delegates sideways: no design system → run `manage-design-system` first; image input → hand upload to `upload-to-stitch`, then refine via its own edit flow. The README's selective-install warning is the flip side: skills have inter-dependencies, and a partial install that drops a delegate breaks the flow.
- **Per-agent support is an install-mechanics matrix, not a fork.** Same library, six hosts: Codex (marketplace + sparse checkout), Claude Code / Cursor (`npx plugins`, project/workspace scope), Gemini CLI and Antigravity (named compatible in the standard's host list), OpenCode (manual: copy skill folders into `.opencode/skills/` — it also discovers `.claude/skills/` and `.agents/skills/` — plus a hand-written remote-MCP entry in `opencode.json`). OpenCode exposes the adaptation cost plainly: `stitch::…` names must be renamed to lowercase kebab-case to load, extra frontmatter (`allowed-tools`) is ignored, and tool names inside instructions may need swapping to host builtins.

## Fleet mapping (candidate fits — unscored, intake only)

- **Skill package shape** ↔ the fleet's skills library: SKILL.md + scripts-as-enforcers + references-as-knowledge-base + examples-as-gold-standard is the fleet's own skill anatomy, externally standardized — and the `plugin.json` bundle layer above skills is a grouping/marketplace primitive the fleet library currently lacks.
- **Instruction layer over one MCP server** ↔ connector discipline: capability lives in exactly one server; each agent host consumes it through a thin per-surface instruction pack, with prefix/tool-name drift absorbed at the host boundary — the fleet's connector pattern with documentation as the adapter.
- **DESIGN.md / SITE.md as steering artifacts** ↔ the fleet's persistent-steering-file method (CLAUDE.md-class): one portable Markdown contract that generators read and appliers enforce, versioned with the project.
- **Contender contrast (unscored):** Pax composes capabilities *in-process* (a capability is code snapped onto the agent); Stitch Skills compose *instructions over a remote MCP* (the skill is prose + references; the server is the code). Same field — agent capability/plugin surfaces — opposite placement of the executable weight. The DoE leg scores the placement, not this entry.
