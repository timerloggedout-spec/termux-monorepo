## The pattern (what we copy)

- **Workflows are durable TypeScript scripts, not config.** A workflow is a `.ts` file in `~/.t3/workflows/` (server watches the folder, hot-reloads valid edits) written against globals — `T3`, `Effect`, `Schema`, `Option`, no imports — as an Effect generator: `workflow("release", { version: 1, payload: Schema.Struct({...}) }, Effect.fn(function* (payload) { … }))` composing `step(...)` (typed `returns`), `agent` steps, `ask(...)`, `title(...)`, `stop(...)`. Authoring is agent-first: a shipped `t3-workflows` skill drops into the agent's own skills folder (`~/.claude/skills/`, `~/.agents/skills/`) and the agent writes the workflow.
- **Durability = checkpointed steps in a server-side store.** Each completed step is checkpointed (workflow store + run records are first-class persistence, migrations in-tree), so a restart resumes the run where it left off instead of restarting it. Turning the Labs flag off pauses existing runs; turning it back on resumes them. Versioning is coexistence: keep older workflow versions defined while they have unfinished runs, bump `version` to deploy new steps alongside active ones, and `start --key` deduplicates starts across retries and version bumps.
- **Human approval is an `ask` step — a designated point, answered in a queue.** `ask("ship", { title, choices })` parks the run at that step until a person answers; choices can be rich objects (`{ value, description, requireReason }` — an answer can require an explanation), context rides as `links`, and the answer is recorded with `answeredAt`/`answeredBy` as part of the run record. Questions are declared by kind (`asks: { kindKey: "Label" }`) and surface filtered under **Needs you** in the app and `t3 workflow questions --kind`. A `signal` (CLI, MCP, or another workflow) answers a question or wakes a channel wait — signals sent before the wait exists are buffered 7 days by default; `withdraw` cancels an open question so `ask` returns `None` and the script decides what that means.
- **Triggers are schedules, webhooks, and forge events — with intake discipline.** Schedules: `every` (interval) and `daily` (local time of day; skipped if missed by >10 minutes while offline). Webhooks: each hook gets a secret path (`t3 workflow hooks`); retries are deduplicated by delivery header (e.g. `X-GitHub-Delivery`), bodies >1 MiB are rejected, starts are rate-limited to 60 runs/min (`429`), and managed policy can disable webhooks outright. Issue/PR triggers fire on new issues or PRs (polled ~every minute, only items opened after the workflow first loads). The docs draw the scope line themselves: a single prompt on a timer or webhook is a *scheduled task*; a workflow is for multi-stage pipelines (triage → fix → approval → release).
- **Concurrency is declared as pools, not managed by hand.** A whole-workflow cap (`concurrency: 4` in options) plus step pools — `within("builders", { limit: 4 }, ...)` fences a section, `limit: 1` acts as a lock; waiting runs show as **Queued** in FIFO order and resumed runs re-acquire their pools first. A shared key-value `store` (`t3 workflow store get/set`) persists state between runs.
- **Agent steps are ordinary threads.** Each `agent` step runs in a regular thread (hidden from sidebar lists) that a person can open live from the run, with its own `workspace`, `runtimeMode`, `interactionMode`, and typed `returns`, including on linked remote environments. Failure semantics differ by step kind: failed code steps auto-retry after 5, 20, and 80 minutes (or immediately on Resume); failed or timed-out agent steps pause for manual resume; cancelling a run stops active agent turns and child runs permanently. Up to 500 skipped runs per workflow are retained (configurable).
- **One project spans several repositories.** A project folder need not be a repo itself: T3 auto-discovers every Git repository inside it (one level down, plus one level deeper inside non-repo folders), imports `.code-workspace` files, accepts external folders per machine (up to 128), and treats submodules as first-class (modified submodules appear as their own repository for diffs and Git actions). Per-repo exclusions live in the project folder's `t3.json` (`ignoreRepositories`). Turn diffs group by repository; commit/push/PR actions run per repository, PRs link under their own repo.
- **Worktree isolation is per repository, on one thread branch.** A worktree thread gets a folder matching the project layout, with each selected repository given its own worktree on the thread's branch (branched from the thread's base branch where one exists, else the repo's default). Files in the plain project folder outside repositories are linked (shared), not copied. Custom layouts are scripts in `t3.json` (`worktreeLayout.create/remove`) run under an env contract (`T3_WORKTREE_ROOT`, `T3_WORKTREE_BRANCH`, `T3_WORKTREE_REPOSITORIES`, …) — and the exact command strings are **approval-gated per environment**: stored approvals invalidate when the string changes, unapproved commands block worktree creation from mobile, scheduled tasks, and agents, and agents can never approve them. Rewind restores every repository to an earlier snapshot and reports any repo it skipped.
- **The control plane drives other people's agents on the user's own subscriptions.** Claude Code, Codex, Cursor, OpenCode, Grok Build, Antigravity, Kiro, Pi, Muse, fx, and any ACP agent — "if an agent is set up on your computer, T3 Code can control it." No tokens are resold; models switch mid-thread and agents hand tasks to each other. One server serves desktop, web, iOS, and Android clients with the same threads; remote machines connect over LAN, Tailscale, or T3 Connect, and v0.1.12's linked threads (beta) read and connect to threads on linked machines without pairing each machine first. MCP sign-in happens from the thread warning itself, including on remote environments — credential repair at the point of failure.

## Maturity signals (at intake, 2026-11-26)

- Repo `pingdotgg/t3code`: MIT license, TypeScript, ~80.6k stars / ~14.2k forks / ~3.8k open issues, created 2026-02-08 — under a year old and moving extremely fast: v0.1.12 shipped 2026-11-25 with 1,092 changes from 226 contributors, nightlies land daily (v0.1.13 nightlies already out), and the 100 most recent releases span only back to 2026-11-04.
- Beta flags are explicit: Workflows, linked threads, and the connections map are all beta in v0.1.12; Workflows are Labs-gated (`Settings → Labs → Workflows`, or `"workflowsEnabled": true` in `~/.t3/userdata/settings.json` on headless servers).
- Durability has a stated boundary: runs only advance while the server that started them is online — this is restart-surviving local execution, not hosted execution.
- Install surface: desktop apps (macOS/Windows/Linux — `brew install --cask t3-code`, `winget`/`scoop`, AUR, Nix, `.deb`), CLI via `curl -fsSL https://t3.codes/install.sh | sh` or one-off `npx t3@latest`, plus iOS/Android apps. Free and open source; the agents it drives run on the user's own subscriptions.
- The implementation is in-tree and inspectable: `apps/server/src/workflows/` (engine, runtime, store), persistence migrations 110–119 (workflows, skipped runs, run indexes/tags, pools, mail sender), an MCP workflow toolkit, and a full `t3 workflow` CLI — agents themselves can start, signal, answer, and inspect runs.

## Fleet mapping (candidate fits — unscored, intake only)

- **Durable workflow + `ask` gate** ↔ QUE machinery + HOTL. T3's approval hold is the closest product relative of the fleet's HOTL so far: the human is engaged at a designated step and nowhere else, and the answer (with `answeredBy`/`answeredAt`, optional required reason) is part of the run record rather than a comment convention. The differences are the instructive part: T3's hold is *in-run and synchronous* — the run waits at the step and advances only while its one server is online, and the person answers in the product's Needs-you queue — where fleet HOTL keeps the hold as QUE state (Board's `blocked --kind awaiting_approval` is the same idea as a queue state) so the system carries the wait across surfaces and the human answers where the work already lives. T3 = HOTL compiled into a single-server runtime; the fleet's version stays deliberately looser-coupled.
- **Checkpointed steps + version coexistence** ↔ the VM replacement rhythm: runs that survive restarts and resume mid-pipeline, with old definitions kept alive for in-flight runs, are the same discipline as the fleet's checkpointed/chunked jobs under a ~2h replacement cadence — a worked implementation of resume-don't-restart to inspect.
- **Step pools (`limit: 1` = lock, FIFO Queued, resume re-acquires first)** ↔ FLY-001 claim/lease discipline: concurrency fencing declared in the workflow instead of negotiated by claim stamps — a contrasting implementation to set beside Board's lease + `claim_lost` fencing when the fleet compares claim mechanisms.
- **Webhook dedup + 60/min cap + policy kill-switch** ↔ quota-aware intake: deduplicating triggers by delivery ID and hard-capping starts is the fleet's pre-flight headroom doctrine applied at the trigger surface — nothing fires unbounded just because the outside world knocked.
- **Multi-repo projects + per-repo worktrees** ↔ the monorepo + per-entry repo family (`delphi-oracle`, `moneyball`, `repo-story`, `understudy`): one thread, one branch name, an isolated worktree per repo, per-repo PRs — the fleet's entry-repo shape worked from a single project. The `worktreeLayout` approval gate (exact-string approval, invalidated on change, agents can never approve) is a concrete command-approval pattern worth keeping next to the fleet's own approval-card discipline.
- **Agent-agnostic control plane over ACP** ↔ the wrapped-session model: T3 drives whatever agent CLI is installed and treats the harness as the durable layer — the fleet's "surface is a participant, the stack is ours" split (DeepAgent.py→core.py), at desktop scale and pointed the other direction (many agents, one harness).
