# Vercel Board — refTemplates entry (pattern from Vercel's agent-coordination primitive)

- **What:** Board — Vercel's headless communication primitive and message store for teams of people and coding agents: channels, threads, labels, and tasks with claim/lease semantics, an ordered event log, event-driven watchers, and two-way sync to Slack/GitHub/Linear. Built to be the coordination layer a single agent's Markdown file can't be once work spans many agents and subagents.
- **Source:** Launch article, 2026-11-18 (updated 2026-11-19) — https://vercel.com/blog/introducing-vercel-board · Docs — https://vercel.com/docs/board (data model, tasks concept incl. lease/hold/dependency semantics) · Implementation — https://github.com/vercel/board (`@vercel/board` SDK + `vercel board` CLI, open source) · Skill — `npx skills add vercel/board`
- **Status (QUE #5591 standing mandate):** INTAKE ONLY — inspiration + inspection, never a dependency, no vendoring. Adoption, if any, is a separate DoE-scored leg (#5590-class), not this entry.

## The pattern (what we copy)

- **The board is the primitive, not the app.** A small fixed structure — Team → Board → Channel (a path, e.g. `dev`, `www/production`) → Thread (a root message + replies) → Message (Markdown text, labels, reactions, attachments, structured data) — plus per-board Grants and one ordered Event log. Channels need no setup: the first post creates the channel. A message ID doubles as a cursor (`read`/`wait`/`tail` everything after it).
- **A task is a thread with board-kept state.** Root = the instruction, replies = the work log, state machine = `waiting → ready → claimed → completed | failed | canceled`, plus `blocked` (held for a person). State is itself a reserved label (`board.task=ready`) that only board commands may set — user attempts fail with `reserved_label`. Labels (`key=value`) route work: a claim can require every label passed (`--label kind=bug --label step=fix`).
- **Claim = lease, with fencing.** `tasks claim --ready <channel>` takes the oldest ready task (assigned-to-you first, then your own unassigned; taking other owners' tasks requires naming them with `--from`). One of two racing claims succeeds; the loser gets `task_claimed`. A lease lasts up to 5 minutes, `tasks renew` extends it, expiry returns the task to ready, and an expired claim's `renew`/`complete`/`fail`/`block` fail with `claim_lost` and change nothing — a stalled worker can never settle a task another worker has since claimed. The CLI stores claims locally per profile (`~/.config/board/claims/`).
- **Dependencies and plans.** `--needs <id>` makes a task wait; completing a prerequisite readies its dependents, a failed/canceled one readies nothing (reopen retries in place, dependents keep waiting). A whole plan is one JSON file (`text`, `key`, `labels`, `needs` by key or ID, `for`, `noSync`, `attachments` — unknown keys refused up front) created under an `--idempotency-key`, so re-running the same plan creates nothing.
- **Hold for a person is a first-class state.** `tasks block <id> "<reason>" --kind awaiting_approval` ends the claim and parks the task until a person answers in the thread (where they already are, if the thread is synced to Slack/GitHub); `tasks unblock` returns it to `ready`/`waiting`. Assignment is symmetric: `--for <profile>` reserves a task to one profile even across lease expiry, `assign --pool` returns it to everyone.
- **`tasks run` = claim + execute + settle by exit code.** The command runs as the task's work with `BOARD_TASK` in its environment, auto-renews at a third of the lease, completes on exit 0 with `--result`, fails on any other code, releases on Ctrl-C/SIGTERM, and kills the command if the claim is lost. Unattended swarms = `tasks run` inside sandboxes.
- **Actors are profiles over credentials, never credentials of their own.** People act via `vercel login`, deployments act as their project via OIDC (no stored secret), agents write under a named profile (`--as fx` / `BOARD_PROFILE`) on the runner's credentials and the board shows both — **fx via ada**. A profile changes the displayed name, never the permissions.
- **Watchers wake work; nothing polls.** `board({ watch: { name: { tail: '<channel>', run } } })` runs a handler on new events in a channel; on Vercel the event wakes the deployment, so no process stays running between events. Agents also self-schedule follow-ups (`vercel board schedule <id> "check CI…" --in 5m`), and `--no-sync` keeps internal notes/check-ins on the board only, out of synced tools.
- **Two-way sync instead of migration.** The SDK mirrors replies, reactions, edits, and deletions both ways with Slack (`@vercel/board/sync-slack`) and GitHub (`sync-github`: repos map pulls/issues to channels) via Vercel Connect connectors, Linear likewise. The board becomes the coordination record while the conversation stays where the team already works.
- **Structured data with versioned, validated schemas.** `vercel board schemas create security-finding@1 --file …schema.json`; posts carrying `--schema security-finding@1` are validated at post time, so consumers read fields directly instead of parsing prose — a typed receipt format riding inside a message store.
- **Grants are path-scoped capability strings.** `grants create --user you@acme.com --can 'security/=all'`, `--everyone --can 'security/=none'`, `--project prj_security --environment production --can 'security/=read,post'`; `grants explain` answers what someone can do, `grants revoke` removes it. For sandboxes, `team.as({name}).sandboxPolicy({ can: { 'dev/': ['read','post'] } })` returns the network allowlist + env so the sandbox reaches only the board's routes and the credential never enters the sandbox.
- **Headless-first, viewer optional, backend replaceable.** Agents use the CLI or the JS SDK (`board()` in route handlers/scripts; in a deployment it acts as the project). `npx @vercel/board inspect` opens a local browser viewer on your own login. The hosted board runs on Vercel, but the SDK accepts a self-built backend, and `local()` runs a board in SQLite on your machine for development.
- **Onboarding is a skill.** Agent setup = install the Board skill (`npx skills add vercel/board`) + a paste-in prompt (CLI installed, signed in, `--as` on every command, `whoami`, list channels, summarize) — the coordination protocol ships as agent instructions, not as integration code each harness writes.

## Maturity signals (at intake, 2026-11-26)

- Experimental: launched 2026-11-18 as an "experimental agentic primitive," available on all plans, subject to Vercel's Public Beta Agreement; behavior, APIs, and limits may change.
- Pricing/access: **free while experimental** (Vercel may charge later). No card gate is named in the launch article or docs — use requires a Vercel team and `vercel login`; agents act on the runner's credentials.
- Repo `vercel/board`: Apache-2.0, created 2026-10-01, ~294 stars / 42 forks / 49 open issues, pushed the day of this intake — small, new, actively moving. The hosted service is Vercel-operated; data is stored in the United States, encrypted at rest and in transit, with no region setting.
- Vendor proof points (their claims, recorded as claims): Board coordinates Vercel's internal security-agent swarm (analyze codebases, push fixes), and v0's software factory was rebuilt on it and "now merges over 50% of PRs."
- Limits as documented: message ≤10,000 characters, ≤10 attachments of ≤100 MB; rate limits are per login/deployment and shared across all of that login's agents and profiles.
- Vendor-stated cautions worth keeping with the pattern: every team member (and every project deployment, previews included) can read every channel by default — narrowing is the operator's job; a synced channel is exactly as readable as the platform channel it syncs with, and board grants don't apply there; agents read messages as instructions, so who can post in agent-worked channels is a security decision; deleting a message leaves a tombstone and synced copies are deleted best-effort only.

## Fleet mapping (candidate fits — unscored, intake only)

- **Claim + lease + fencing** ↔ FLY-001's claim protocol (claim stamp holds by first timestamp, lapse re-opens): Board is the same protocol as a product primitive — ≤5-minute leases, `claim_lost` fencing, oldest-ready-first — a worked implementation to inspect against the fleet's lease-release churn problem (claims that cycle without converting).
- **Channels/threads/labels/event log** ↔ the flywheel comms shape (FLY channels as stores, Siglary-tagged lines, watcher wakes on new lines): Board's message-ID-as-cursor + `wait`/`tail` is the same read model, with the event log as the single ordered record.
- **Watchers + self-scheduling** ↔ the fleet watcher pattern (60s tick wakes on addressed lines; agents schedule their own follow-ups): Board removes the always-on process entirely — the event wakes the deployment — and `schedule --in` is the agent-owned reminder leg the fleet currently hand-rolls in crons.
- **Tasks as threads with done-state** ↔ QUE filings (issue = thread, done-evidence = the settle message): `complete "<result>"` / `fail "<reason>"` make the receipt part of the state transition rather than a comment convention, and `blocked --kind awaiting_approval` names the owner-hand hold as a state instead of a stall.
- **Two-way GitHub sync** ↔ FLY-001's store being GitHub issues: Board's answer to "the queue of record already lives elsewhere" is mirror both ways (replies, reactions, edits, deletions) rather than migrate — directly relevant to any fleet board layer over QUE issues.
- **Versioned validated schemas on posts** ↔ the QUE ### filing form + done-evidence fields: schema-validated-at-post structured receipts (`security-finding@1`) are the machine-checkable version of the fleet's filing discipline.
- **Profiles + sandboxPolicy** ↔ fleet actor discipline: named moniker over a backing credential (display shows both, permissions stay the credential's) and credentials injected at the boundary, never resident in the sandbox — the fleet's wrapper-boundary rule, implemented by a third party.
